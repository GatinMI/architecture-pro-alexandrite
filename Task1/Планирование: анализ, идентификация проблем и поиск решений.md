# Планирование: анализ, идентификация проблем и поиск решений

## 1. Понимание текущего состояния

### 1.1 Состав системы (по C4-модели и описанию)

| Система | Фронтенд | Бэкенд | База данных |
|---|---|---|---|
| Онлайн-магазин | Vue, TypeScript, Three.js | Shop API (Spring Boot) | Shop DB (PostgreSQL) |
| CRM | Vue | CRM API (Spring Boot) | **Своей БД нет** — работает напрямую с Shop DB |
| MES | React | MES API (C#) | MES DB (PostgreSQL) |

Дополнительные компоненты: RabbitMQ (обмен сообщениями между CRM и MES, «несколько топиков»), S3-хранилище файлов 3D-моделей.

### 1.2 Потоки заказов

**B2C (онлайн-магазин):**
Клиент → Shop (Vue) → Shop API → Shop DB; 3D-файл загружается в S3.
`INITIATED` → `FILE_UPLOADED` → `SUBMITTED` (онлайн-магазин, Shop DB).
MES читает файл из S3 и считает стоимость (2–30 минут) → `PRICE_CALCULATED` (MES DB).
Продавец подтверждает в CRM → `MANUFACTURING_APPROVED` (записывается в Shop DB).
Операторы в MES: `MANUFACTURING_STARTED` → `MANUFACTURING_COMPLETED` → `PACKAGING` → `SHIPPED` (MES DB).
Отправка/закрытие в CRM → `CLOSED` (Shop DB).

**B2B (открытый API):**
Пользователь API → **напрямую в MES API** (открытый для партнёров API — это внешний интерфейс MES API, который используется для приёма заказов и расчёта стоимости изделия).
MES отправляет сообщение в RabbitMQ → CRM создаёт заказ → дальше статусы аналогично B2C.

### 1.3 Ключевые особенности инфраструктуры и процессов

- По одному EC2-инстансу на приложение, горизонтального масштабирования и HA нет.
- По одному инстансу БД на систему (запись + чтение), реплик нет.
- RabbitMQ — единый инстанс.
- CI/CD: dev — автоматически после мержа и юнит-тестов; release и prod — ручные деплои.
- QA: E2E-сценарии прогоняются вручную на тестовом окружении; баги high/highest блокируют релиз, задержки релиза растут.

## 2. Идентификация проблем

### 2.1 Бизнес-симптомы (то, что ломается сейчас)

| # | Симптом | Источник |
|---|---|---|
| S1 | B2C-клиенты не получают заказы в срок: обещали 3 недели, фактически месяцы | Жалобы менеджерам по продажам |
| S2 | После открытия API (Q2) поток заказов резко вырос, просрочки стали ещё хуже | Жалобы, потерянные контракты |
| S3 | B2B-клиенты (пользователи API) «не получают свои заказы» | Ежедневные сообщения партнёров |
| S4 | Дашборд MES (список заказов по статусам) грузится долго; фильтр по статусам и пагинацию не помогли | Жалобы операторов |
| S5 | Потеряно несколько крупных B2B-контрактов; растёт недовольство B2C-клиентов | Продакт-менеджер, продажи |
| S6 | Релизы регулярно задерживаются: QA на ручном E2E находит high-баги, версия ждёт исправлений | Процесс выпуска |

Производство — не бутылочное горлышко (мощности позволяют удвоить объём). Бутылочное горлышко — в софте.

### 2.2 Технические проблемы (причины)

- **P1. Ограниченная пропускная способность расчёта стоимости.** Расчёт — долгая (2–30 минут), ресурсоёмкая операция, длительность зависит от числа полигонов. Выполняется в MES на единственном инстансе, параллельность ограничена возможностями одного EC2/процесса. Это главное узкое место всей цепочки: заказы накапливаются до производства, хотя производство способно обрабатывать вдвое больше. Ориентировочно: 10 параллельных расчётов при средней длительности 3 минуты — потолок ~200 заказов/сутки; с учётом доли моделей, считающихся до 30 минут, потолок заметно ниже. При росте потока (+100 заказов/мес + всплеск B2B) очередь на расчёт растёт быстрее, чем успевает обрабатываться.
- **P2. Тяжёлый расчёт выполняется внутри MES API.** Тот же процесс/инстанс, который обслуживает дашборд и операции операторов. Долгие задачи (до 30 минут) занимают пул потоков и ресурсы БД — одна из причин медленного дашборда (S4).
- **P3. Дашборд MES и перегруженная БД.** Единственный инстанс MES DB обслуживает и записи, и чтения. Запрос «список заказов по статусам, свежие сверху» почти наверняка не оптимизирован: отсутствуют индексы под фильтр/ORDER BY, таблица растёт. Тот факт, что фильтр + пагинация не помогли, говорит: проблема не в интерфейсе, а в запросе и/или загрузке БД.
- **P4. Нет гарантий надёжности интеграции MES ↔ CRM.** Заказы передаются между системами сообщениями RabbitMQ, при этом (по описанию и схеме): нет идемпотентности потребителей, не видно DLQ/повторов, нет мониторинга потока сообщений, нет сквозного отслеживания заказа. Потерянное сообщение или простой CRM = потерянный/зависший заказ. Это прямое объяснение S3 («не получили заказ») и части S1 (заказы «зависают» между статусами, и никто об этом не знает).
- **P5. Статус заказа распылён по двум БД.** Стартовые статусы, `MANUFACTURING_APPROVED` и `CLOSED` — в Shop DB (CRM своей БД нет и пишет туда), производственные статусы — в MES DB. Единого источника истины «где сейчас заказ» не существует: невозможно построить сквозной трекер, SLA-контроль и внятный ответ клиенту.
- **P6. CRM связан с Shop DB напрямую** (database coupling, антипаттерн). Два приложения на одной БД: связанность релизов, риск неконсистентности, взаимное влияние на производительность.
- **P7. Открытый B2B-API — это сам MES API.** Нет отдельного гейтвея/факада: нет rate-limit/квот, нет идемпотентности при создании заказа, нет вебхуков/колбэков со статусами, нет SLA, нет изоляции от внутренней нагрузки. Партнёры падают на тот же инстанс, на который падают операторы MES. Это объясняет потерю B2B-контрактов (S5) и ухудшение S4.
- **P8. Нет наблюдаемости и мониторинга.** Нет сквозного мониторинга потока заказов, нет алертов «заказ застрял в статусе X на N часов», нет бизнес-метриков (глубина очередей, время расчёта, просроченные заказы), нет SLO. Проблемы обнаруживаются через жалобы клиентов — когда ущерб уже нанесён.
- **P9. Нет коммуникации с клиентами и партнёрами.** Нет уведомлений о смене статусов, нет прогресса расчёта стоимости (до 30 минут тишины), нет оценки сроков исполнения заказа.
- **P10. Процесс выпуска и качество.** Ручной E2E, релиз блокируется high-багами, ручные деплои в release/prod. Задержки релиза растут (S6): цикл выпуска не масштабируется вместе с системой. Нет нагрузочного тестирования, канареечных релизов, быстрого отката.
- **P11. 3D-модели: нет контроля сложности.** При загрузке не оценивается количество полигонов/время расчёта, нет нормализации/упрощения моделей, нет предварительной оценки сроков для пользователя. Чем детальнее модели (а новые рынки — новые дизайны), тем сильнее ухудшается P1.

### 2.3 Потенциальные риски (что сломается дальше)

| # | Риск |
|---|---|
| R1 | Неограниченный рост таблиц заказов/статусов без партиционирования и архивации — дальнейшее деградирование БД (дашборд уже страдает) |
| R2 | По одному инстансу на EC2, БД и брокер — SPOF по каждому звену: без HA и DR любой сбой останавливает весь поток заказов |
| R3 | B2B-рост: без rate-limit/квот пользователи API нагрузят MES ещё сильнее — эффект «завала» повторится и усилится |
| R4 | SLA в B2B-контрактах, которые система не может гарантировать (нет трекинга, нет лимитов) — пени и новые потери контрактов |
| R5 | 3D-файлы в S3 растут без lifecycle-политик; время расчёта растёт с детализацией моделей — узкое место P1 со временем ухудшится |
| R6 | Команда — ограничение: один DevOps, QA без автоматизации, релиз зависит от ручной регрессии. При текущем темпе роста это потолок скорости изменений |
| R7 | Ручные деплои без канареек и отката: инцидент в prod имеет большой MTTR и бьёт по всем каналам (B2C + B2B) одновременно |

## 3. Инициативы

| # | Инициатива | Суть | Устраняет |
|---|---|---|---|
| I1 | **Масштабируемый асинхронный конвейер расчёта стоимости.** Вынести расчёт из MES API в отдельные воркеры-сервисы; запуск по событию (заказ создан / файл готов); очередь задач с авторасширением по глубине очереди; контроль параллельности и SLA-классы (быстрые/долгие модели); публикация результата и прогресса расчёта. | P1, P2, R3 (частично) |
| I2 | **Быстрый выигрыш: производительность дашборда MES.** Профиль slow-query и индексов MES DB («список по статусам», «свежие сверху»), read-реплика для дашборда, сводная/материализованная таблица или кэш «свежих заказов», на фронте — server-driven пагинация и виртуализация списка. | P2, P3, S4 |
| I3 | **Надёжность потока заказов.** Идемпотентные потребители, DLQ и повторы для потоков RabbitMQ, outbox-паттерн для публикации, регулярная сверка (reconciliation) статусов заказов между Shop/MES/CRM, алерты «заказ завис в статусе» (SLA на каждый статус), обработка dead-letter и консоль для администраторов. | P4, P5 (частично), S1, S3 |
| I4 | **B2B-API как отдельный фасад/гейтвей.** Отдельная точка входа перед MES: аутентификация и квоты на клиента, rate-limit, идемпотентное создание заказа, вебхуки/колбэки о статусах, версионирование и документация, SLA и его мониторинг, изоляция B2B-трафика от операторов MES. | P7, S3, S5, R4 |
| I5 | **Единый источник истины по статусу заказа (E2E-трекинг).** Объединённый реестр статусов заказа (на базе событий), доступный CRM, MES, магазину и API-пользователям: «где мой заказ» для всех каналов, основа для SLA и отчётности. | P5, S1, S3 |
| I6 | **Наблюдаемость и SLO.** Сквозная трассировка потока заказа, бизнес-метрики (заказы/день, время расчёта, глубина очередей, просроченные заказы), алерты (зависшие заказы, загрузка БД/брокера), дашборд для менеджмента и операций, явные SLO по каналам (B2C, B2B). | P8, все симптомы |
| I7 | **Инфраструктура: масштабирование и отказоустойчивость.** Авторасширение MES API и воркеров расчёта (ASG), read-реплики БД, RabbitMQ в HA, бэкапы/DR, blue-green/канареечные деплои. | P2, R2, R7 |
| I8 | **Отвязка CRM от Shop DB.** Заменить прямой доступ к Shop DB на события/API; провести границу данных между магазином и CRM. | P6 |
| I9 | **Процесс выпуска и автоматизация тестов.** Автоматизировать E2E-регрессию (прототипы QA-инженера), staging с данными, близкими к prod, обязательное нагрузочное тестирование перед релизами с ростом трафика, канареечный релиз и быстрый откат, критерии релиза без «стены high-багов». | P10, S6, R6, R7 |
| I10 | **Опыт клиента и партнёра.** Уведомления о смене статусов (email/вебхуки), индикатор прогресса расчёта в магазине, оценка сроков изготовления, публичный статус API для пользователей B2B-API. | P9, S1, S3 |
| I11 | **Контроль сложности 3D-моделей.** Проверка числа полигонов и оценка времени расчёта при загрузке, нормализация/сжатие, фоновое упрощение тяжёлых моделей в очереди. | P11, P1 |
| I12 | **Команда и процессы.** Найм бэкенда (MES, C#) под конвейер и platform-инженера (DevOps/SRE); выстроить автоматизацию QA; архитектурный обзор крупных изменений. | R6, ресурс для I1–I9 |

## 4. Приоритизация

### 4.1 Критерии

Рейтинг выстроен по пяти критериям:
1. **Бизнес-эффект** — насколько прямо останавливает потери и жалобы (контракты, SLA, отток клиентов).
2. **Снижение риска** — насколько уменьшает вероятность полного срыва потока заказов.
3. **Скорость** — трудозатраты для команды из 8; быстрый выигрыш даёт импульс и доверие.
4. **Разблокирующее действие** — сколько следующих инициатив зависят от этой.
5. **Устойчивость к росту** — хватит ли архитектуры на двукратный рост и расширение B2B.

### 4.2 Порядок

**P0 — первые 1–2 месяца (спринты 1–4):**

1. **I1 — конвейер расчёта стоимости.** Единственная мера, которая снимает корневую причину главной жалобы (просрочки). Пока расчёт не вынесен и не масштабируется, очередь заказов перед производством будет расти, как бы мы ни чинили дашборд. Разблокирует двукратный рост производства и частично разгружает MES API (дашборд, B2B).
2. **I3 — надёжность потока заказов.** Вторая по тяжести жалоба («заказы не доходят») затрагивает и B2C, и B2B, и является прямой причиной потерянных контрактов. Идемпотентность + DLQ + сверка + алерты на зависшие заказы также дают первые данные мониторинга — фундамент для I6 и для ответа партнёрам.
3. **I2 — производительность дашборда MES.** Быстрый выигрыш, который можно выпустить как hotfix в первые 1–2 недели параллельно с I1/I3: дёшево, заметно для пользователей, частично разгружает БД. Операторы видят свежие заказы (от этого зависит их вознаграждение) → быстрее забирают заказы в работу → производственная мощность реально используется.

**P1 — следующие 3–6 месяцев:**

4. **I4 — B2B-API фасад.** Возвращает доверие партнёров и делает новый канал выручки предсказуемым. Часть эффектов (rate-limit, идемпотентность) «зашить» можно уже в рамках I3/I4-базы на ранних этапах, но полноценный фасад с вебхуками, квотами и SLA — отдельный эпик.
5. **I6 — наблюдаемость и SLO.** Растёт органически из I1/I3 (метрики конвейера, алерты на зависшие заказы); к концу полугодия — сквозной трейсинг, бизнес-дашборд, SLO по каналам.
6. **I10 — уведомления клиентам и партнёрам.** Прямо снижает объём жалоб даже при плотных сроках; реализуется поверх трекинга (I3) и вебхуков (I4).
7. **I9 — процесс выпуска и тестирование.** Освобождает пропускную способность релизов; нагрузочные тесты перед релизом — защита от повторения «потолок найден в проде».
8. **I7 — инфраструктура.** ASG и read-реплики для MES частично утягиваются в I1/I2; остаток (HA брокера, DR, blue-green) — вторая половина периода.

**P2 — 6–12 месяцев:**

9. **I5 — единый источник истины по статусу заказа.** Стратегический рефакторинг поверх уже событийных потоков; даёт «где мой заказ» для всех каналов и основу SLA-отчётности.
10. **I8 — отвязка CRM от Shop DB.** Осмысленно делать только после I5/I3, когда границы данных стали очевидны; раньше это перекладывает проблему.
11. **I11 — оптимизация 3D-моделей.** Важно для долгосрочного (время расчёта растёт с детализацией), но на старте его сглаживает очередь из I1.
12. **I12 — команда.** Найм — ресурс, а не самоцель: бэкенд под I1 начинать найм в первый месяц, platform-инженера — ко второй половине (I7/I9).

### 4.3 Обоснование ключевых решений

- **I1 — первый**, потому что это единственная мера, снимающая ограничение по пропускной способности. Все жалобы о просрочках (S1, S2, часть S5) — следствие ограниченной скорости расчёта. Без неё остальные меры маскируют симптом: заказы всё равно будут копиться.
- **I3 — второй**, потому что «исчезающие заказы» — самый дорогой симптом (теряются контракты), а исправление относительно дёшево (идемпотентность, DLQ, сверка). Одновременно создаёт данные, на которых строятся I5 и I6.
- **I2 — третий по порядку, но первый по релизу**: hotfix на 1–2 недели, который снимает боль операторов и даёт команде быстрый видимый результат.
- **I4 — после I1/I3**: красивый фасад поверх ненадёжного конвейера ситуацию не спасёт; а главные причины недовольства партнёров (заказы не создаются, статус не виден) покрываются уже I3. Временная мера (rate-limit и идемпотентность на существующем эндпоинте) делается вместе с I3.
- **I5/I8 — вторая половина года**: это рефакторинг данных, который нужно делать спокойно, поверх работающего мониторинга (I6) и предсказуемого процесса релизов (I9).

## 5. Целевая архитектура через полгода

Ключевые принципы: **событийный поток заказа, вынесенный и масштабируемый расчёт, stateless-сервисы с горизонтальным масштабированием, единый источник истины по статусу, бизнес-мониторинг потока заказов**.

Целевой поток заказа:

```
B2C:  Shop --> Shop API --> [событие: заказ создан, файл в S3] ----+
B2B:  API-пользователь --> B2B-API фасад --> [то же событие] -----+
                                                                    v
                                    очередь расчёта (RabbitMQ, DLQ)
                                                                    v
                        воркеры расчёта стоимости (auto-scaling, SLA-классы)
                                                                    v
                    [событие: PRICE_CALCULATED] --> CRM: подтверждение (MANUFACTURING_APPROVED)
                                                                    v
                    MES API (оператор: взятие в работу, выполнение, упаковка, отправка)
                                                                    v
                    [события статусов через RabbitMQ, идемпотентно] --> CRM: CLOSED
                                                                    v
                 Order Tracking: E2E-статусы «где мой заказ», алерты на зависшие заказы
```

Изменения по компонентам:

| Компонент | Сейчас | Через полгода |
|---|---|---|
| MES API | 1 EC2; API + тяжёлый расчёт в одном процессе | Stateless, 2+ инстанса (ASG + балансировщик), без долгих задач |
| Расчёт стоимости | Внутри MES API, ограниченная параллельность | Отдельные воркеры, авторасширение по глубине очереди, SLA-классы, прогресс расчёта |
| B2B-API | Прямой внешний доступ к MES API | Отдельный фасад: аутентификация, rate-limit, квоты, идемпотентность, вебхуки, SLA |
| MES DB | 1 инстанс на чтение + запись | Первичный + read-реплика; индексы под ключевые запросы; план архивации истории |
| Дашборд MES | Медленный единый запрос | Читает с read-реплики/сводной таблицы: «свежие заказы» мгновенно, без влияния на запись |
| RabbitMQ | 1 инстанс, гарантии не описаны | HA; идемпотентные потребители, DLQ, мониторинг потока; публикация через outbox |
| CRM | Работает напрямую с Shop DB | Потребляет события; доступ к данным магазина через API (начало отвязки) |
| Order Tracking | Отсутствует (статусы в двух БД) | E2E-реестр статусов для всех каналов, алерты на SLA-нарушения |
| Наблюдаемость | Отсутствует | Метрики, трейсинг, SLO, бизнес-дашборд, алерты |
| Релизы | Ручной E2E, ручные деплои | Автоматическая регрессия, нагрузочные тесты, канарейка, быстрый откат |

Сознательно **не делаем** за полгода: миграцию на микросервисы «ради микросервисов», замену RabbitMQ и СУБД, полный переезд CRM со своей моделью данных. Сначала — поток, надёжность и наблюдаемость; структурный рефакторинг (I5, I8) — после, по готовым метрикам и мониторингу. Обновлённая C4-схема целевой архитектуры — материал задания 2.

## 6. Три пункта, если можно выполнить только три за ближайшие полгода

1. **I1 — масштабируемый асинхронный конвейер расчёта стоимости** (включая базовый мониторинг: глубина очереди, время расчёта).
   Единственная мера, снимающая корневую причину главной проблемы — накопление очереди заказов и срыв SLA «3 недели». Разблокирует двукратный рост производства, разгружает MES API (частично лечит дашборд) и становится той архитектурой, на которой B2B-канал сможет расти. Без неё всё остальное — симптоматика.
2. **I3 — надёжность потока заказов + алерты на зависшие заказы** (идемпотентность, DLQ, сверка статусов, обработка dead-letter; как часть — первые бизнес-метрики потока).
   Останавливает самый дорогой симптом — «заказы исчезают» (потерянные B2B-контракты, недовольство B2C). Дает управлению впервые видимость конвейера: просрочки видны до того, как о них расскажут клиенты.
3. **I2 — производительность дашборда MES** (индексы/запросы, read-реплика, кэш «свежих заказов»).
   Дешёвый быстрый выигрыш, выпускаемый за первые 1–2 недели: разгружает людей, которые реально производят, и даёт команде доверие и импульс, пока строятся I1 и I3.

Почему не другие:
- **I4 (B2B-фасад)** — важен, но его ключевая ценность для партнёров (заказы не теряются, статус виден) обеспечивается I3; полноценный фасад с вебхуками и SLA — первый пункт второго полугодия. Временные меры (rate-limit, идемпотентность) делаются внутри I3.
- **I6 (наблюдаемость)** — не самостоятельный пункт, а обязательная часть I1 и I3: без алерта на зависший заказ I3 не работает, без метрик I1 слеп.
- **I5/I8 (реестр статусов, отвязка CRM)** — крупные рефакторинги, которые корректно делать во втором полугодии, поверх I1/I3/I6.

Результат трёх пунктов: поток заказов становится быстрее (расчёт), надёжнее (заказы не теряются, зависшие видны) и операторы работают без тормозов. Это покрывает все четыре текущих потока жалоб: B2C-просрочки, B2B «не получили заказ», API-пользователи «не получили заказ», медленный дашборд.

## 7. Команда и ресурсы (обоснование найма)

Текущей команды из 8 на I1–I3 и базу I4/I6 не хватает. Обоснование:

- **+1 бэкенд-разработчик (C#, MES)** — с первого месяца. Единственный C#-разработчик не может одновременно поддерживать MES (а он будет под нагрузкой и в инцидентах) и строить конвейер расчёта, идемпотентность и дашборд.
- **+1 platform/DevOps-инженер** — со второй половины периода (I7/I9). У одного DevOps на 3 окружения и 4 сервиса работы по платформе (ASG, реплики, канарейки, нагрузочные стенды) будет постоянно уходить в подождание за «пожаротушением».
- **QA-инженер** — не новый найм, а направление: автоматизация E2E-регрессии (на его прототипах) как часть I9. Это снимает «стену high-багов» с релизов.
