# Выбор и настройка мониторинга в системе

---

## 1. Мотивация

### 1.1. Почему мониторинга сейчас недостаточно

Сайт «Александрит» подключён к Яндекс Метрике, но Метрика измеряет только поведение пользователей на фронтэнде (просмотры страниц, клики, технический успех загрузки). Она **не покрывает** то, из-за чего компания теряет заказы:

1. **Потерянные и «зависшие» заказы.** Клиенты (и B2B-партнёры) сообщают, что заказы не получены, хотя обещанный срок — 3 недели. Заказы создаются асинхронно через очередь RabbitMQ между CRM и MES и через внешний API (MES API), и в этой асинхронной цепочке нет ни одного технического средства увидеть, **на каком этапе заказ застрял и с момента какого времени**. Метрика об этом не говорит ничего: для пользователя сайт при этом работает «нормально».
2. **Рост нагрузки после открытия API.** Каждый месяц +100 заказов, а после открытия API — скачок. При этом каждое приложение крутится на **одном инстансе**, БД — на одном инстансе на чтение и запись. Ни у кого нет ответа на вопросы: выдержит ли Shop API / MES API / БД текущий рост, где начнётся деградация, и когда нужно масштабировать. Сейчас решения о масштабировании принимаются «на авось», по жалобам.
3. **Медленный дашборд MES.** Операторы жалуются на медленную загрузку списка заказов в работе. Фильтр по статусам и пагинация не помогли — значит, проблема глубже (скорее всего, тяжёлые запросы к БД). Чтобы подтвердить гипотезу и отслеживать эффект от правок, нужны метрики латентности конкретного эндпоинта и метрики БД (долгие запросы, соединения).
4. **Качество интеграции CRM ↔ MES.** Интеграция через RabbitMQ написана собственной командой, и именно через неё проходят заказы, включая заказы от внешних API-пользователей. Упавший консьюмер, сообщения в dead-letter-очереди, растущая глубина очереди — всё это сегодня обнаруживается через жалобы клиентов, а не через систему.
5. **Расчёт цены — узкое место.** MES считает стоимость 2–3 минуты в среднем и до 30 минут на сложных моделях. Это долго по дизайну, но если расчёт зависает навсегда, никто не знает. Нужны метрики длительности и количества параллельных расчётов.
6. **Отчётность перед B2B-партнёрами.** Партнёры по API ежедневно сообщают о неполученных заказах. Чтобы отвечать на их претензии фактами (объём, ошибки, задержки по их клиенту), нужны данные с метриками по каждому партнёру.

### 1.2. Что мониторинг даст компании (аргументы для бизнеса)

- **Обнаружение проблем до жалоб клиентов.** Сегодня мы узнаём о потере заказа через месяц, когда клиент звонит менеджеру. С мониторингом — в течение минут: сообщение в DLQ, рост очереди, зависший расчёт цены, деградация латентности дашборда MES. Это напрямую снижает число потерянных заказов и контрактов (уже потеряно несколько крупных).
- **Измеримый SLA по этапам заказа.** Мы сможем показать менеджерам и B2B-партнёрам, сколько времени заказ проводит на каждом этапе, и где теряются недели. Это превращает «над изделием работают несколько месяцев» в конкретный этап с конкретным временем.
- **Обоснованные решения о масштабировании.** Рост +100 заказов/мес и запуск API требуют понимания нагрузки. Метрики RPS, латентности, использования CPU/памяти/соединений БД дадут ответ «когда и что масштабировать», а не после срыва SLA.
- **Данные для приоритизации работы над дашбордом MES.** Понимание, какой именно запрос тормозит список заказов, позволит сфокусировать усилия и измерить эффект от оптимизации.
- **Контроль издержек.** Рост S3-хранилища (3D-модели), размера БД и загрузки инстансов — это будущие деньги. Мониторинг покажет тренды роста и позволит запланировать расширение раньше, чем появится инцидент.

### 1.3. Оправдание затрат для бизнеса

Чтобы внедрение мониторинга было понятным бизнесу решением, фиксируем его стоимость:

| Статья | Оценка |
|---|---|
| Инфраструктура (один небольшой инстанс для VictoriaMetrics, Grafana, Alertmanager + exporters; либо управляемая TSDB в Yandex Cloud) | 5-15 кРублей/мес |
| Разработчики (инструментализация 3 API + бизнес-метрики) | ~2–3 спринта частичного участия (см. раздел 5) |
| DevOps (развёртывание стека, алерты) | ~1–2 спринта |
| QA (проверка срабатывания алертов) | ~0.5 спринта |

Контраст: **один потерянный крупный контракт уже обошёлся дороже**, чем годовая стоимость этого мониторинга. Мониторинг — это не «ещё одна инициатива», а инструмент, который защищает выручку от основной текущей проблемы компании.

## 2. Выбор подхода к мониторингу
В разных частях системы мы применяем разные подходы:

| Часть системы | Подход | Обоснование |
|---|---|---|
| Shop API, CRM API, MES API (веб-сервисы, request-driven) | **RED** | Это высоконагруженные request-driven сервисы. Для них естественны: интенсивность запросов (RPS), доля ошибок (Errors), время отклика (Duration). RED отвечает на вопрос «видит ли пользователь проблему?». MES API дополнительно обслуживает внешний B2B-трафик — для него RED критичен из-за SLA перед партнёрами. |
| Инстансы EC2 (CPU, память, сеть, диск) | **USE** | Для вычислительных ресурсов главное — заполненность: Utilization (CPU, память, сеть), Saturation (очереди, перегрузка), Errors (ошибки ОС/диска). RED на уровне инстанса не применим — там нет «запросов». |
| БД PostgreSQL (Shop DB, MES DB) | **USE** | Для СУБД ключевые ресурсы — соединения, память (кэш), диск, I/O. Отслеживаем их использование и насыщенность (использование пула соединений, активные сессии, долгие запросы). |
| RabbitMQ (очереди, интеграции) | **USE + специфичные метрики очередей** | Очереди — главный источник «потерянных» заказов. Измеряем глубину очереди, dead-letter, сообщения в полёте, lag консьюмеров. Это по сути Saturation/Errors для асинхронного канала. |
| S3-хранилище (3D-файлы) | **USE (размер, ошибки запросов)** | Хранилище — ресурс: отслеживаем заполненность (размер, количество объектов) и ошибки при загрузке/чтении. |
| Заказ как бизнес-объект (SLI/SLA по этапам) | **Бизнес-метрики поверх «золотых сигналов»** | Главный болевой сигнал — «заказ завис на этапе N». Это не технический RED/USE, а измерение времени нахождения заказа в каждом статусе (см. 3.7). Фактически мы дополняем технические сигналы бизнес-сигналом, который напрямую отражает жалобу клиента. |

**Итог:** RED для request-driven сервисов, USE для ресурсов (инстансы, БД, очереди, хранилище), плюс слой бизнес-метрик (SLI/SLA по этапам заказа), который связывает технические сигналы с деньгами. Четыре золотых сигнала мы покрываем как «супернабор»: latency/traffic/errors — в RED, saturation — в USE и в отдельных метриках насыщенности (раздел 6).

## 3. Метрики, которые будем отслеживать

### 3.1. Общие правила для ярлыков (labels)

Чтобы не «раздуть» time-series базу, зафиксировать правила:

1. **Низкая кардинальность.** В ярлыках — только значения из ограниченного набора: `env` (dev/release/prod), `app` (shop|crm|mes), `instance` (id инстанса), `endpoint` (шаблон маршрута вида `/api/orders`, **не** URL с идентификаторами заказов), `method`, `status_code` (класс 2xx/4xx/5xx + точные коды 5xx), `partner` (id B2B-партнёра — ограниченное множество), `queue`/`exchange`/`topic` (ограниченный набор очередей), `db` (shop|mes), `unit` (для бизнес-метрик).
2. **Запрещено** в ярлыках: id пользователя, id заказа, id 3D-модели, токен, сырые URL с query-параметрами.
3. **Все метрики** — counter, gauge или histogram (для латентности считаем percentiles p50/p95/p99); интервал скрейпинга — 15–30 с.

### 3.2. Прикладные сервисы (Shop API, CRM API, MES API) — подход RED

| Метрика (из списка) | Зачем нужна | Ярлыки |
|---|---|---|
| **Number of requests (RPS) for internet shop API** | Базовый сигнал нагрузки и тренда (растёт ли трафик B2C). Позволяет сравнивать текущий трафик с базовой линией и выявлять всплески после кампаний/сбоев. | `env`, `endpoint`, `method`, `status_class` (2xx/4xx/5xx) |
| **Number of requests (RPS) for CRM API** | CRM обслуживает менеджеров-продавцов; деградация их API = простой продаж. Низкий трафик, но важная точка: резкий рост RPS CRM API часто означает лавину повторных запросов фронтенда при сбое. | `env`, `endpoint`, `method`, `status_class` |
| **Number of requests (RPS) for MES API** | Ключевая после открытия API: сюда пришёл новый внешний B2B-трафик. Разделяем внутренний и внешний трафик, чтобы видеть, какой долей нагрузки являются партнёры, и держать SLA перед ними. | `env`, `endpoint`, `method`, `status_class`, `partner` (для внешнего сегмента: id партнёра) |
| **Number of HTTP 500 for shop API** | Ошибки 5xx — прямой сигнал сбоя, который видят пользователи (и партнёры по API). На неё строим алерт по порогу доли 5xx. Трактуем шире: counter 5xx с точным кодом (500/502/503/504), чтобы отличать ошибку кода от недоступности зависимости. | `env`, `endpoint`, `method`, `status_code` |
| **Number of HTTP 500 for CRM API** | Аналогично; сбои CRM API ломают работу менеджеров и (критично) приём заказов из очереди от MES, если они не обрабатываются. | `env`, `endpoint`, `method`, `status_code` |
| **Number of HTTP 500 for MES API** | Критично для B2B-партнёров: 5xx на их запрос = прямой жалобный сигнал. Плюс сигнал проблем на internal-эндпоинтах MES. | `env`, `endpoint`, `method`, `status_code`, `partner` |
| **Response time (latency) for shop API** | Восприятие пользователя: медленная витрина/корзина = потеря продаж. Смотрим p95/p99 по эндпоинтам, чтобы находить конкретные медленные маршруты (не «в среднем»). | `env`, `endpoint`, `method`, `status_class` |
| **Response time (latency) for CRM API** | Удобство работы менеджеров; деградация проявляется как «CRM тормозит» в часы пика продаж. | `env`, `endpoint`, `method`, `status_class` |
| **Response time (latency) for MES API** | **Прямой адрес главной жалобы операторов**: медленный дашборд — это конкретный эндпоинт списка заказов. Отслеживаем его p95/p99 отдельно, чтобы подтвердить/опровергнуть гипотезу о тяжёлом запросе к БД и измерить эффект оптимизаций. | `env`, `endpoint`, `method`, `status_class`, `partner` |
| **Number of simultanious sessions for shop API** *(интерпретируем как одновременные in-flight запросы)* | Для stateless REST «сессии» = активные в работе запросы (занятые треды Tomcat/пула). Это метрика насыщенности: если in-flight растёт, а RPS нет — сервис «захлёбывается». | `env` |
| **Number of simultanious sessions for CRM API** *(in-flight)* | То же для CRM; важно при пиках (например, массовая рассылка подтверждений). | `env` |
| **Number of simultanious sessions for MES API** *(in-flight)* | Особенно важно: дорогие операции (расчёт цены) держат запросы/ресурсы долго. Рост in-flight при стабильном RPS — индикатор зависших расчётов. | `env` |
| **CPU % for shop API** | USE-Utilization для инстанса: понимание, какой запас прочности есть до масштабирования (рост +100 заказов/мес). | `env`, `instance` |
| **CPU % for CRM API** | То же для CRM. | `env`, `instance` |
| **CPU % for MES API** | То же для MES; MES API теперь несёт и B2B-нагрузку, и долгие расчёты цены — CPU здесь первичный индикатор перегрузки. | `env`, `instance` |
| **Memory Utilisation for shop API** | JVM-приложения: следим за heap (used/committed) — медленный рост = утечка памяти, которая со временем приведёт к OOM и простоям. | `env`, `instance`, `area` (heap/non-heap) |
| **Memory Utilisation for CRM API** | То же. | `env`, `instance`, `area` |
| **Memory Utilisation for MES API** | То же; плюс контекст: долгие расчёты цены могут держать большие объекты в памяти. | `env`, `instance`, `area` |

**Дополнительные метрики для прикладных сервисов** (вне списка, добавляем сознательно):

| Метрика | Зачем | Ярлыки |
|---|---|---|
| Доля 4xx по API (особенно MES API по `partner`) | 4xx на API-эндпоинтах B2B — маркер плохой интеграции партнёра (неправильные запросы, просроченные ключи). Позволяет проактивно помогать партнёрам, а не ждать жалоб. | `env`, `endpoint`, `partner` |
| JVM GC-паузы (p99) | Длинные GC-паузы — незримый источник «случайных» торможений (в том числе дашборда MES). | `env`, `instance`, `gc` |
| Active threads в пуле Tomcat (использование пула) | Насыщенность: занятость тред-пула -> 503 при исчерпании. | `env`, `instance` |
| **Время расчёта цены в MES (histogram)** | Ядро бизнес-сценария: распределение длительности расчёта (2–30 мин). Смотрим квантили, чтобы видеть: средний случай vs хвост; фиксируем, если расчёт длится **больше** известных 30 мин (завис). | `env`, `model_complexity` (легко/тяжело, если доступно), `result` (success/failure/timeout) |
| **Количество параллельных расчётов цены (gauge)** | Конкурентные расчёты — главная нагрузка на MES. Если параллельных «тяжёлых» расчётов больше, чем ресурсов, новые запросы будут долго ждать — видим это до жалоб. | `env` |
| Ошибки/таймауты расчёта цены (counter) | Сбой расчёта = заказ не может уйти в производство, а пользователь не получил цену. Отдельный алерт. | `env`, `reason` |
| **Загрузка файлов 3D в S3 (успех/ошибка, длительность p95)** | Файл — обязательная часть заказа (`FILE_UPLOADED`). Ошибки загрузки блокируют оформление; длительность влияет на UX. | `env`, `result` |

|---|---|---|

| **Memory Utilisation for MES db instance** | То же для MES DB; особенно важно для тяжёлых запросов дашборда (список заказов по статусам). | `db`, `instance` |

| **Number of connections for mes db instance** | То же для MES DB. | `db`, `instance`, `app` |
| **Size of shop db instance** | Тренд размера БД (линейный рост заказов + метаданные 3D-моделей). Прогноз исчерпания диска; плановое масштабирование Managed DB вместо аварийного. | `db`, `instance` |
| **Size of MES db instance** | То же для MES DB. | `db`, `instance` |

**Дополнительные метрики БД** (добавляем сознательно — они напрямую связаны с жалобой на медленный дашборд):

| Метрика | Зачем | Ярлыки |
|---|---|---|
| Использование пула соединений приложениями (active/idle/max, HikariCP) | Точнее, чем «соединения в БД»: показывает, какое приложение приближается к исчерпанию своего пула. | `db`, `app`, `pool_state` |
| **Долгие/медленные запросы (p95 query time, число запросов > 1с, > 10с)** | Прямой индикатор проблемы дашборда MES: если запрос списка заказов идёт долго — это и есть причина. Позиционируем запрос, а не «ощущение». | `db`, `app`, `query_id` (хеш, ограниченное множество) |
| Активные сессии / блокировки (lock waits) | Конкурентные блокировки — причина «случайных» торможений при пике (много операторов одновременно). | `db` |
| I/O и utilisation диска, cache hit ratio | USE для БД: деградация I/O или кэша -> рост латентности запросов. | `db`, `instance` |
| Размер таблицы заказов + индексов (trend) | Конкретно для дашборда: рост таблицы при неподдерживаемых индексах = деградация запросов. Позволяет спланировать партиционирование/архивацию. | `db` |

### 3.4. Очереди RabbitMQ — главная зона «потерянных заказов»

Это самая важная секция: заказы теряются именно в асинхронной интеграции CRM ↔ MES.

| Метрика (из списка) | Зачем нужна | Ярлыки |
|---|---|---|
| **Number of dead-letter-exchange letters in RabbitMQ** | **Критичная метрика.** Сообщение в DLQ = заказ, который кто-то из приложений не смог обработать. Каждый такой message — потенциально потерянный заказ. Алерт на **любое** появление в DLQ (порог 0). | `exchange`, `queue`, `app` (кто отправлял), `reason` |
| **Number of message in flight in RabbitMQ** | Сообщения, отданные консьюмеру, но ещё не подтверждённые (unacked). Рост in-flight при стабильном трафике = консьюмер завис (например, долгий расчёт цены удерживает ack). | `queue`, `app` (консьюмер) |

**Дополнительные метрики очередей** (добавляем сознательно — без них «in-flight» не интерпретируется):

| Метрика | Зачем | Ярлыки |
|---|---|---|
| **Глубина очереди (ready messages) по каждой очереди** | Насыщенность: растущая глубина = производитель не успевает за потребителем, задержка обработки заказов. Алерт по порогу глубины и **скорости роста**. | `queue`, `topic` |
| **Время жизни сообщения в очереди (p95, max)** | Насколько долго заказ ждёт обработки в очереди. Прямой вклад в SLA «3 недели». | `queue`, `topic` |
| **Lag / задержка консьюмеров (consumer lag)** | Разница между тем, что накопилось, и тем, что обработано. Позволяет быстро найти «отстающий» консьюмер (CRM или MES). | `queue`, `app` |
| Количество консьюмеров в работе (up/down) | Падение консьюмера (например, после планового рестарта MES API) — причина роста очереди. Алерт на 0 активных консьюмеров на критичной очереди. | `queue`, `app` |
| Соединения publishers/consumers (up/down) | Разрыв соединения = messages не публикуются/не потребляются. | `app` |

### 3.5. S3-хранилище 3D-файлов — подход USE

| Метрика (из списка) | Зачем нужна | Ярлыки |
|---|---|---|
| **Size of S3 storage** | 3D-модели накапливаются; рост = рост стоимости и риск исчерпания квоты. Прогноз по тренду. | `env`, `bucket` |

**Дополнительно:** количество объектов (trend), ошибки/доля 5xx на операции put/get, размер среднего объекта. Ошибки put/get уже учтены в метрике загрузки/чтения 3D-файлов (3.2).

### 3.6. Инфраструктура EC2 (все инстансы) — USE

В список из задачи не входят явные метрики ОС/инфраструктуры, добавляем сознательно (node_exporter), так как каждый сервис на одном инстансе, и его ресурсный предел — наш потолок масштабирования:

| Метрика | Зачем | Ярлыки |
|---|---|---|
| CPU %, память, своп, сеть (rx/tx), I/O диска | Базовый USE для всех инстансов (Shop API, CRM API, MES API, инстансы мониторинга). Позволяет увидеть деградацию «до того, как упадёт сервис». | `instance`, `app`, `env` |
| **Kb transferred (received) / Kb provided (sent) for shop / CRM / MES API** *(из списка, включаем как сетевой I/O инстанса)* | Сетевая нагрузка: резкий рост трафика (например, массовые загрузки 3D-файлов через Shop API) — индикатор нового типа нагрузки или проблемы. Приоритет ниже, чем CPU/память, но полезно для capacity-планирования. | `instance`, `app`, `direction` (rx/tx) |

### 3.7. Бизнес-метрики по жизненному циклу заказа (SLI/SLA)

Технические метрики отвечают «что сломалось в системе». Но главная боль бизнеса — «где застрял заказ». Поэтому добавляем слой бизнес-метрик, которые строятся поверх данных о статусах заказа (информация о статусах уже есть в Shop DB / MES DB).

**Источник:** заказы и их статусы хранятся в Shop DB (с точки зрения CRM/магазина) и MES DB (с точки зрения производства). Для измерения достаточно раз в 1–5 минут выполнять **лёгкие** агрегирующие запросы (COUNT / MIN по статусам) на управляемых БД — нагрузка пренебрежима по сравнению с боевой.

| Метрика | Зачем нужна | Ярлыки |
|---|---|---|
| **Количество заказов по каждому статусу** (INITIATED, FILE_UPLOADED, SUBMITTED, PRICE_CALCULATED, MANUFACTURING_APPROVED, MANUFACTURING_STARTED, MANUFACTURING_COMPLETED, PACKAGING, SHIPPED, CLOSED) | «Светофор» конвейера. Резкий накоп в статусе (например, скачок в `PRICE_CALCULATED`) — сразу видно, где конвейер забился. Это прямое отражение жалобы «над изделием работают месяцами». | `env`, `status` |
| **Время нахождения заказа в статусе (age, histogram/gauge по квантилям)** | Прямой SLI: сколько дней заказ простаивает в каждом статусе. Позволяет вычислить фактический цикл «3 недели» и найти конкретный этап, где теряется время. | `env`, `status` |
| **Заказы, зависшие в статусе дольше порога (gauge счётчик)** | Готовая алертная величина: например, заказы в `MANUFACTURING_APPROVED`/`MANUFACTURING_STARTED` старше N дней, в `PRICE_CALCULATED` старше 30 мин. Алерт на рост этого числа. | `env`, `status`, `threshold` |
| **Скорость создания заказов по каналам** (counter: web B2C / API B2B) | Видим раздельный вклад B2C и B2B в нагрузку и тренд +100/мес. Позволяет количественно оценить эффект открытия API и планировать ёмкость. | `env`, `channel` (web|api), `partner` (для api) |
| **Доля заказов, вовремя закрытых (CLOSED ≤ SLA)** | Итоговая бизнес-KPI-метрика: процент заказов, прошедших цикл за обещанный срок. Это «одна цифра» для отчёта руководству. | `env`, `channel` |
| **Доля заказов, прошедших через DLQ / требующих ручного вмешательства** | Косвенный показатель качества интеграции CRM↔MES. Рост = интеграция деградирует. | `env` |

## 4. Технологический стек мониторинга (черновик решения)

Выбираем стек с учётом: (1) всё в Yandex Cloud, (2) 9 человек в команде + 1 DevOps, (3) малое количество инстансов (3 API + БД + очереди), (4) нужна историческая справка (тренды по месяцам).

| Компонент | Выбрать | Обоснование |
|---|---|---|
| **Сбор метрик (экспортеры)** | node_exporter (EC2), Micrometer + Prometheus registry (Shop/CRM на Spring Boot), prometheus-net или OpenTelemetry (MES на C#), rabbitmq_exporter (RabbitMQ), postgres_exporter / метрики управляемых БД YC, небольшой self-hosted скрейпер бизнес-метрик (агрегаты по статусам заказов) | Стандартный, дешёвый, low-maintenance набор. Spring Boot уже поддерживает Micrometer «из коробки». |
| **Time-series база** | **VictoriaMetrics** (single-node), либо управляемая TSDB в Yandex Cloud | Одна легковесная binary; хорошо масштабируется по retention и кардинальности; поддерживает Prometheus-совместимый API (remote write / scrape); дешевле и проще в эксплуатации, чем кластер Prometheus для наших объёмов. |
| **Визуализация** | **Grafana** | Готовые дашборды (RED, USE), алерты, шеринг со стеком VM; команда уже знакома с графиками. |
| **Алерты** | **Alertmanager** -> Telegram (команда) + почта; для critical — «звонилка» (телефон/Telegram voice) | Telegram — основной канал коммуникации команды; быстрый и привычный. |
| **Хранение/логирование (опционально, фаза 2)** | Loki (logs) + correlation id | Метрики скажут «что», логи с trace-id скажут «почему». Вводим на 2-м этапе, когда метрики стабилизируются. |

**Инфраструктура:** один небольшой инстанс (например, 4 vCPU / 8 GB) в отдельной сети мониторинга, на котором VictoriaMetrics + Grafana + Alertmanager. Экспортеры — рядом с наблюдаемыми инстансами (sidecar) или собираются центральным скрейпером. Ретеншн: 30–90 дней в высоком разрешении (15–30 с), агрегированные (hourly) — 12+ месяцев для трендов.

**Окружения:** внедряем в **prod** и **release**; **dev** — базовый мониторинг (тот же стек, меньше алертов), чтобы видеть регрессии на ранней стадии.

## 5. План действий (драфт технического задания)

Высокоуровневый план по фазам. Оценка — в спринтах (2 недели); участники — из текущей команды + DevOps.

### Фаза 0. Каркас (0.5–1 спринт, DevOps)

1. **Создать инстанс time-series базы** — VictoriaMetrics (single-node) на отдельном EC2 (4 vCPU / 8 GB) в Yandex Cloud, либо подключить управляемую TSDB (VictoriaMetrics) в YC, если решим не вести собственный инстанс.
2. **Развернуть Grafana и Alertmanager** на том же или отдельном инстансе; настроить доступ (внутренняя сеть + доступ по IP/SSO для команды).
3. **Настроить централизованного скрейпера** (Prometheus / vmagent) с интервалом 15–30 с и remote write в VictoriaMetrics; настроить ретеншн (30–90 дней raw, 12 месяцев hourly).
4. **Развернуть node_exporter** на инстансах Shop API, CRM API, MES API (и инстансе мониторинга).
5. Каналы алертинга: Alertmanager -> Telegram (канал мониторинга) и почта; определить «первого дежурного» (в первые 2 месяца — тимлид).

### Фаза 1. RED-метрики приложений (1 спринт, Java-инженеры + C#-инженер)

6. **Shop API и CRM API (Java):** подключить Micrometer + Prometheus registry, открыть `/actuator/prometheus`; экспонировать счётчики запросов (RPS) с ярлыками `endpoint`, `method`, `status_class`, тайм-серии длительности (p50/p95/p99), in-flight запросы, JVM heap/GC.
7. **MES API (C#):** подключить prometheus-net (или OpenTelemetry) и те же метрики; добавить ярлык `partner` на внешние API-эндпоинты (B2B).
8. **Дашборды Grafana** «RED per service» (3 дашборда: shop/crm/mes) + дашборд «Overview» для быстрого взгляда.
9. **Первые алерты:** 5xx > 1% за 5 минут (critical), p95 превышение базовой линии (warning), CPU > 80% / память > 90% за 10 минут (warning).

### Фаза 2. Ресурсы: БД, RabbitMQ, S3 (1 спринт, DevOps + бэкенд)

10. **RabbitMQ:** развернуть rabbitmq_exporter; настроить сборку: глубина очередей по topic, in-flight (unacked), DLQ-счётчики, число консьюмеров, время жизни сообщений.
11. **БД:** подключить метрики управляемых PostgreSQL (через API Yandex Cloud Monitoring / prometheus-скалер): соединения, память, размер, I/O, активные сессии; для Shop DB — раздельный учёт соединений по приложениям (ярлык `app`). Если доступ к `pg_stat_statements` доступен через админ-интерфейс YC — включить сборку медленных запросов.
12. **S3:** метрики размера/объектов объекта хранения через API YC; ошибки put/get дублируются метрикой приложения (загрузка 3D-файлов).
13. **Дашборды:** «Databases», «Message Queue», «Object Storage».
14. **Алерты (ключевые):** любое сообщение в DLQ (critical), 0 активных консьюмеров на критичной очереди (critical), глубина очереди > порога (warning/critical, см. раздел 6), соединения БД > 70%/90% (warning/critical).

### Фаза 3. Бизнес-метрики и дашборды для команды (1 спринт, Java + C# + продакт)

15. **Скрейпер бизнес-метрик** (небольшое приложение на Java или Go, чтение только): каждые 1–5 минут — count заказов по статусам, возраст заказов в статусах (квантили), счётчики «зависших» заказов; публикация в Prometheus-формат.
16. **MES API:** добавить histogram длительности расчёта цены, gauge параллельных расчётов, счётчики ошибок/таймаутов расчёта.
17. **Дашборды для бизнеса:** «Order pipeline» (светофор по статусам + age), «B2B партнёры» (RPS/5xx/latency по `partner`), «Отчёт SLA» (доля заказов, закрытых вовремя).
18. **Алерты:** заказы в `PRICE_CALCULATED` > 30 мин (warning), «зависшие» заказы > порога (warning), доля заказов вне SLA растёт (warning для PM).
19. **Документация:** runbook по каждому critical-алерту (что проверить, кому позвонить, как переслать сообщение), страница с ответом на вопрос «что делать, если...» для операторов и менеджеров.

### Фаза 4. Стабилизация и расширение (после 2 недель в работе, все)

20. **Гигиена алертов:** недельный ретроспективный разбор всех алертов — убрать шум, откалибровать пороги (цель: ≤ 5 critical-алертов в неделю, каждый actionable).
21. **QA:** автоматизировать «chaos-проверку» на release — остановить консьюмера MES / перегрузить очередь и убедиться, что алерты сработали (отличный первый проект для QA-инженера, который хочет автоматизацию).
22. **Фаза 2 (опционально):** Loki + correlation id в логах для перехода от «что» к «почему»; RUM (Web Vitals) в Метрике/отдельном инструменте для фронтэнда (LCP/INP/CLS) — дополнит метрику латентности API пользовательским ощущением.
23. **Ежемесячный capacity-ревью** (архитектор + DevOps + PM): тренды RPS, размер БД/S3, CPU — прогноз на 2–3 месяца вперёд, решение о масштабировании (scale-up EC2 / масштабирование Managed DB) до того, как порог станет critical.

**Суммарно до полного MVP (фазы 0–3): ~3 спринта частичной загрузки команды** — примерно по 0.25–0.5 FTE на каждого из: 1 DevOps (лидер), 2 Java, 1 C#, 1 QA, 1 PM (смыслы/SLA). Это совместимо с текущим ритмом спринтов без найма; дополнительный DevOps-инженер имеет смысл нанимать, только если появится фаза 2 (логи) + отказоустойчивость мониторинга (2 инстанса, HA).

## 6. Показатели насыщенности: пороги и реакции

Насыщенность (saturation) — это «насколько заполнена» очередь/ресурс. Это самый ранний сигнал перегрузки: деградация начинается не тогда, когда ресурс на 100%, а когда очередь начала расти. Ниже — пороги и обязательные действия.

**Методология порогов.** Порог задаём в двух координатах: (1) абсолютный предел ресурса (максимум соединений, размер диска, тред-пул) и (2) бизнес-обязательство — **SLA «3 недели» на заказ** и **до 30 минут на расчёт цены**. Warning ставим на уровне, когда до исчерпания остаётся запас на 1–2 недели при текущем росте (+100 заказов/мес, плюс B2B). Critical — когда SLA уже находится под риском в ближайшие часы/дни. Все пороги — стартовые: после 2 недель работы алертами их калибруем под реальный фон (ежемесячный capacity-ревью).

| # | Показатель (метрика) | Warning | Critical | Почему именно эти значения | Что должно происходить при превышении |
|---|---|---|---|---|---|
| 1 | **Сообщения в DLQ (RabbitMQ)** | > 0 за 5 мин | > 5 за 15 мин | DLQ — это потерянные/необработанные заказы. Нормальное состояние — 0. Каждое сообщение = потенциально потерянный заказ. | **Немедленно:** тикет в трекер (автоматически из Alertmanager), уведомление в Telegram + **телефонный звонок дежурному** (critical по умолчанию). Действия: достать сообщения из DLQ, найти причину (упал консьюмер, ошибка валидации), переслать в основную очередь или в ручной пересчёт. Если причина — системный сбой консьюмера MES/CRM: поднять приложение. Отчёт PM с перечислением затронутых заказов (id видим в логах/ДБ, не в метриках). |
| 2 | **Глубина очереди (ready messages) по критичным топикам CRM↔MES** | > 100 сообщений на 15 мин | > 1000 на 10 мин или глубина растёт > 20 мин | Нормальный фон — десятки. 100 ≈ несколько минут задержки при текущей пропускной способности; 1000 ≈ часы задержки — прямо бьёт по SLA «3 недели». | **Warning:** тикет, проверка, что консьюмеры живы и не дегенерируют; уведомление дежурному в Telegram. **Critical:** звонок дежурному, диагностика (упал консьюмер? замедлилась БД? лавина расчётов цены?), при необходимости — ручное масштабирование (scale-up инстанса консьюмера) и информирование PM. Если задержка затрагивает заказы B2B-партнёров — предупредить партнёра (PM). |
| 3 | **In-flight (unacked) сообщения / consumer lag** | in-flight > 50 на 10 мин | consumer lag растёт > 30 мин | Рост unacked при стабильном трафике = консьюмер завис (типично: долгий расчёт цены держит ack, тяжёлый запрос к БД). Это «тихий» сбой, который приводит к #2. | Тикет + Telegram. Проверить, не завис ли конкретный расчёт/запрос (по логам приложения-консьюмера), при необходимости рестарт инстанса консьюмера. После восстановления — убедиться, что очередь рассасывается. |
| 4 | **Параллельные расчёты цены в MES** | > 3 одновременных «тяжёлых» расчёта | > 5 или расчёт длится > 60 мин | Известный максимум расчёта — 30 мин. 3+ тяжёлых расчёта на одном инстансе = очередь внутри MES и рост CPU; расчёт > 60 мин = почти наверняка завис, а не «сложная модель». | **Warning:** тикет capacity: рассмотреть scale-up MES API / очередь внутри MES (лимит параллельных расчётов + ожидание). **Critical:** звонок; найти зависший расчёт и завершить, клиентов/B2B информировать о задержке расчёта (PM). |
| 5 | **Соединения БД (Shop DB, MES DB)** | > 70% max_connections на 15 мин | > 90% на 5 мин | Shop DB делят два приложения (Shop API + CRM API) — общий потолок. 90% — до исчерпания один шаг, далее новые запросы падают с ошибкой = 5xx для пользователей. | **Warning:** тикет: найти, кто держит соединения (ярлык `app`), проверить утечку соединений (пул HikariCP), при необходимости поднять лимит пула приложения. **Critical:** звонок дежурному; приоритет — восстановить соединения (рестарт проблемного приложения / scale-up БД в YC), тикет, уведомление PM. |
| 6 | **Медленные запросы БД (запросы > 1 с / > 10 с)** | доля запросов > 1 с растёт > 15 мин, или есть запрос > 10 с на эндпоинте дашборда MES | запрос дашборда > 30 с или очередь блокировок | Прямая причина жалобы операторов на медленный дашборд. Порог по эндпоинту дашборда отдельный: p95 > 2 с. | **Warning:** тикет оптимизации (индексы, план запроса); если это дашборд MES — передать бэкенд-инженеру MES как приоритет. **Critical:** звонок; при необходимости временно ограничить/деградировать тяжёлый запрос (кэширование, упрощение), после — нормальный фикс. |
| 7 | **Диск БД (size / utilisation)** | > 70% квоты на 30 дней тренда | > 85% квоты | Полный диск БД = аварийная остановка записи (нельзя создавать заказы). Managed DB в YC расширяется, но это несинхронная операция — нужен запас. | **Warning:** тикет планового scale-up диска (в YC), проверка тренда роста (что растёт — данные? индексы? dead tuples?); при разрастании dead tuples — VACUUM/аналог. **Critical:** срочный scale-up диска в YC (в течение часа), тикет, уведомление руководителя. |
| 8 | **Память БД (Memory Utilisation)** | > 85% на 15 мин | > 95% + рост ошибок/сбоев | Для managed-БД: падение кэш-эффективности -> больше I/O -> рост латентности (в т.ч. дашборда). | **Warning:** тикет: проверить cache hit ratio; при устойчивом превышении — scale-up памяти БД в YC. **Critical:** срочный scale-up, тикет, звонок. |
| 9 | **CPU инстансов приложений (Shop/CRM/MES API)** | > 70% на 15 мин | > 90% на 5 мин | По одному инстансу на приложение — нет «подушки». 90% = деградация латентности и рост 5xx на горизонте минут. Порог привязан к росту +100 заказов/мес: хотим увидеть тренд до критичного. | **Warning:** тикет capacity; если это MES API при росте B2B — рассмотреть scale-up или ограничение параллельных расчётов. **Critical:** звонок; scale-up инстанса в YC (ручной, 15–30 мин), лимитировать тяжёлые операции (расчёты цены), тикет. |

Для B2B-сегмента MES API — ещё и нарушение SLA перед партнёрами. | **Warning:** тикет, диагностика (какой эндпоинт, какая зависимость). **Critical:** звонок; если затронут B2B-сегмент — **письмо партнёру** (PM) с фактом и ETA; фикс/откат, тикет. |

### 6.1. Эскалация и «что делать» — общая модель

1. **Каналы.** Warning -> сообщение в Telegram-канал мониторинга + авто-тикет в трекер (набор: метрика, порог, ссылка на дашборд, runbook). Critical -> то же + **телефонный звонок/voice-уведомление дежурному** (Alertmanager route) + тикет с priority highest. Для B2B-critical дополнительно — обязательное письмо партнёру (отвечает PM).
2. **Дежурство.** С вводом алертов — вращение дежурного (по очереди: тимлид, Java, C#, DevOps). В первые 2 месяца дежурит тимлид. Цель — чтобы любой critical-алерт был принят человеком за ≤ 5 минут в рабочее время.
3. **После каждого critical-инцидента** — короткий разбор (что случилось, сработал ли алерт вовремя, что улучшить). Пороги и runbook-ы корректируются на ежемесячном capacity-ревью.
4. **Анти-шум.** Правило: если алерт сработал и не потребовал действий — его порог/метрика пересматриваются в ближайшем ревью. Цель к концу квартала: каждый critical-алерт = реальный инцидент; ≤ 5 critical/неделю.
5. **Автоматические реакции (фаза 2, опционально).** Для части critical можно автоматизировать: авто-scale-up инстанса/диска БД в YC, авто-рестарт упавшего приложения (health check), авто-повтор сообщения из DLQ. Вводим только после того, как ручные реакции отработаны и понятны — автоматизация неизвестного только усложнит аварийные сценарии.

## 7. Критерии успеха (как поймём, что мониторинг окупился)

- Через 2 недели после запуска: **ни одного «потерянного» заказа, о котором мы узнали только из жалобы клиента** (все потери замечены алертом раньше).
- Среднее время обнаружения (MTTD) системной проблемы: с «недели/месяца (по жалобам)» до **≤ 15 минут** по алертам.
- Дашборд MES: зафиксирован текущий p95, после оптимизации (по данным из метрик #6/13) — снижение p95 ≥ 50% и отсутствие новых жалоб операторов.
- Ежемесячный capacity-ревью проходит по цифрам (тренды RPS, размер БД/S3, CPU), а не по ощущениям.
- B2B-партнёрам предоставляется отчёт по их SLA (по ярлыку `partner`) без ручного сбора данных.
