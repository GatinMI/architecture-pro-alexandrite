## 1. Анализ текущей архитектуры: где заказ «ломается» и «зависает»

Трейсинг нужен не «вообще», а в конкретных точках, где заказ реально теряет видимость. Разберём жизненный цикл заказа по статусам и отметим зоны риска, опираясь на C4-диаграмму (`jewerly_c4_model.drawio`).

### 1.1. Цепочка прохождения заказа

```
[Клиент] -> Интернет-магазин (Vue) -> Shop API (Spring Boot) -> Shop DB
[Пользователь API] -> MES API (C#)                                  \
                                                                    \-> 3D-файл в S3-хранилище
[Продавец] -> CRM (Vue) -> CRM API (Spring Boot) -> Shop DB        /
                                                                    v
                                                        RabbitMQ (очереди/топики)
                                                                    v
                                                        MES API (C#) -> MES DB -> [Оператор]
```

### 1.2. Зоны риска: где заказ может «сломаться» или «зависнуть»

| # | Зона риска | Что может произойти | Почему её «не видно» сейчас | Требуется ли покрывать трейсингом |
|---|---|---|---|---|
| **R1** | **RabbitMQ — очередь «заказ в работу» (Shop/CRM → MES)** | Сообщение о новом заказе/смене статуса публикуется, но консьюмер MES не поднял его (падение приложения, рестарт при деплое, ошибка десериализации). Заказ «висит» в статусе `SUBMITTED`/`MANUFACTURING_APPROVED` бесконечно. | Нет ничего, что связывало бы «публичер» и «консьюмер» по конкретному заказу. Глубина очереди — агрегат, не ответ на вопрос «а где мой заказ?» | **Да — приоритет 1.** Это канал №1 по потерянным заказам (собственная интеграция команды). |
| **R2** | **RabbitMQ — dead-letter очереди (DLQ)** | Сообщение отравлено (валидация, несовместимость версий) и улетело в DLQ. О заказе никто не знает — он просто перестал существовать в рабочем потоке. | DLQ — «тихое» место: без проактивного обхода или трейса, помечающего «сообщение ушло в DLQ», о потере узнают только из жалобы клиента/партнёра. | **Да — приоритет 1.** |
| **R3** | **MES API — приём сообщения из очереди и расчёт цены** | Консьюмер получил сообщение, начал расчёт (2–30 минут), но: (а) процесс упал/перезапущен в середине расчёта — заказ завис между «получено» и `PRICE_CALCULATED`; (б) расчёт завис (модель со слишком сложными полигонами); (в) ошибка расчёта не привела к изменению статуса. | За 2–30 минут расчёта между «получил сообщение» и «записал цену» нет ни одного контрольной точки (checkpoint). Если упало в середине — заказ в статусе «получен, но не посчитан» на неопределённое время. | **Да — приоритет 1.** Это узкое место по длительности и вероятность сбоев самая высокая. |
| **R4** | **Shop API → 3D-файл в S3** | Загрузка 3D-файла прервалась/упала после фиксации `FILE_UPLOADED` в БД. Заказ «завис» с битым/отсутствующим файлом — MES не может считать цену. | Нет связи между статусом заказа и успешностью загрузки файла. Битая загрузка = незаметный зависший заказ. | **Да (частично).** Трейс охватывает HTTP-вызов загрузки; факт целостности файла — отдельная проверка, но trace запроса виден. |
| **R5** | **MES API — список заказов (дашборд операторов)** | Тяжёлый запрос к MES DB — операторы видят «зависание» страницы. Это не потеря заказа, но «зависание» пользовательского опыта. | Медленный запрос виден в логах DB, но не привязан к конкретному вызову дашборда по заказу. | **Да (второй уровень).** Трейс покажет, какой именно подзапрос (БД, пул) тормозит. |
| **R6** | **Внешний API → MES API (B2B-заказы)** | Заказ от партнёра: HTTP-запрос → приём → публикация в очередь → расчёт → ответ статусом. Любое звено может «сломать» контракт SLA перед партнёром. | Партнёр сообщает «не получил заказ», а мы не можем показать, на каком этапе он застрял. Отсутствует сквозной trace от API-запроса до обработки. | **Да — приоритет 2 (высокая цена ошибки — потерянный контракт).** |
| **R7** | **Аутентификация/авторизация** | — | По условию задачи проблем нет. | **Нет.** Исключаем из покрытия (по договорённости). |

### 1.3. Системы, которые следует покрыть трейсингом

Исходя из зон риска, покрываем трейсингом **все точки, через которые проходит заказ**, кроме UI-слоя и auth:

**Покрыть (приоритет 1):**
1. **RabbitMQ** — публикации и консьюмы сообщений о заказах и статусах (R1, R2). *Связь «producer → message → consumer».*
2. **MES API (C#)** — приём сообщений из очереди, расчёт цены, приём внешнего API-заказа (R3, R6). *Долгие операции, highest risk.*
3. **Shop API (Spring Boot)** — создание заказа, загрузка 3D-файла, оформление (R4). *Вход заказа в систему.*
4. **CRM API (Spring Boot)** — подтверждение заказа (`MANUFACTURING_APPROVED`), приём/отправка в очередь (R1).
5. **S3-хранилище** — операция записи/чтения 3D-файла (R4). *Внедрение в span как клиентский вызов.*

**Покрыть (второй уровень):**
6. **MES DB / Shop DB** — SQL-запросы из критичных сервисов (R5, долгие запросы дашборда). *Достаточно client-spans на уровень БД, без instrumentation самого инстанса.*
7. **Внешний API (MES API)** — входные запросы партнёров (R6). *Пропустить trace-id через публичный API для сквозной видимости B2B-заказа.*

**Не покрывать (осознанно):**
- **A-frontend (Vue)** — это приложение без собственного бэкенда-логике; его «запросы» — это вызовы к Shop/CRM API, которые уже покрыты трейсингом. RUM/Web Vitals — отдельная тема (фазы 2).
- **CRM/MES-фронтенды (React/Vue)** — аналогично, UI не является частью цепочки создания заказа.
- **Аутентификация/авторизация** — по условию задачи проблем нет.
- **Managed PostgreSQL-инстансы** как отдельные «сервисы» — покрываются client-spans из приложений (пункт 6).

## 2. Мотивация

### 2.1. Почему системе нужен именно трейсинг (а не только мониторинг)

Мониторинг (метрики, логи) отвечает на вопрос **«что** не так» (очередь растёт, 5xx вырос, БД тормозит). Но главная боль бизнеса — вопрос **«что произошло с конкретным заказом и где он сейчас»**:

> «Клиент ждёт изделие, хотя мы обещали за 3 недели. Над заказом работали месяцами — но мы не можем ответить, **на каком именно этапе** он застрял и **почему**.»

Трейсинг — это **сквозной журнал жизни одного заказа** (и одного запроса): он даёт ответ на «что происходило и где находится сейчас», связывая все события в **один trace** по всем сервисам. Именно поэтому трейсинг — инструмент **решения** текущей проблемы, а не «ещё один слой наблюдаемости».

**Ключевое отличие для нашего сценария:**
- **Метрики** (задание 2): агрегированные сигналы — «глубина очереди N», «p95 дашборда 3 с». Говорят *что* и *сколько*.
- **Логи**: текст построчно, без связи между сервисами. Говорят *подробности*, но не *цепочку*.
- **Трейсинг**: **привязан к одному заказу/запросу** и показываем *полную цепочку* перемещений через все сервисы и очереди с временными метками. Говорит *что происходило с этим конкретным заказом и где он сейчас*.

Без трейсинга у нас есть «симптомы» (метрики), но нет «истории болезни» конкретного заказа — а именно историю требует менеджер продаж, отвечая клиенту, и архитектор, разбирая потерянный контракт.

### 2.2. Что это даст компании

1. **Оперативный ответ клиенту и партнёру по API.** Вместо «мы проверим» менеджер/поддержка может открыть trace конкретного заказа и сказать: «заказ был создан 12:00, расчёт цены начался 12:05, завис 12:31 (расчёт не завершился), причина — падение MES API». Это **прямо конвертируется в сохранение контрактов** (потеряно уже несколько крупных) и снижение жалоб.
2. **Сокращение времени поиска корневой причины (MTTR).** Сегодня диагностика «зависшего заказа» — ручной поиск по логам 3 сервисов + 2 БД + очереди, минуты-часы. С трейсингом — открытие одного трейса.
3. **Видимость асинхронных «провалов».** Ровно в тех точках (R1–R3, R6), где заказы реально теряются: между publisher и consumer, между получением сообщения и завершением расчёта. Это то, чего не дают ни метрики, ни логи.
4. **Опорные данные для SLA-отчётности перед B2B-партнёрами.** Сквозной trace по API-заказу позволяет показать партнёру фактическое время на каждом этапе — аргумент в споре о «неполученном заказе».
5. **Фундамент для автоматического мониторинга заказа (раздел 5).** Трейсинг — источник данных: если мы знаем, какие spanы ожидаются у «здорового» заказа, мы можем автоматически детектировать, что заказ **не прошёл** ожидаемый этап, и алертить. Это превращает «пассивный журнал» в «активного сторожа».

### 2.3. Возможные метрики решения (3–5), на которые повлияет внедрение трейсинга

| # | Метрика (тип) | Как меняется после внедрения трейсинга | Как измерить |
|---|---|---|---|
| **М1** | **MTTD — среднее время обнаружения «зависшего» заказа** (business KPI, часы) | С «месяца (по жалобе клиента)» до **минут** (алерт по отсутствию ожидаемого span / DLQ-span). Прямая защита выручки. | Разница между временем, когда заказ перестал двигаться, и временем, когда команда получила уведомление. Сравнить «до/после» по журналам инцидентов. |
| **М2** | **MTTR — среднее время разбора «зависшего» заказа** (техническая, минуты) | С «часов (ручной поиск по логам 5 систем)» до **минут (открытие одного трейса)**. | Время от открытия инцидента до идентификации этапа/причины. Логировать в тикетах. |
| **М3** | **Доля «зависших» заказов, обнаруженных до жалобы клиента** (business, %) | Растёт к **100%**: все потери обнаруживаются алертом по trace, а не звонком клиента/партнёра. | (зависшие, найденные алертом) / (все зависшие). Замер по итогам месяца после внедрения. |
| **М4** | **Доля заказов с полным сквозным trace (coverage)** (качество, %) | Растёт к **100%** заказов, прошедших конвейер. Низкий coverage = есть незатронутые зоны риска. | (заказы с полным набором ожидаемых span) / (все заказы). Ежедневный автоматический отчёт. |
| **М5** | **Число потерянных заказов / контрактов в месяц** (business KPI, шт.) | Снижается (задачи M1–M3 приводят к раннему восстановлению заказов до их «сгорания»). | Бизнес-показатель от отдела продаж/PM; сравнение месячных трендов. |

## 3. Данные, которые должны попадать в трейсинг

Для каждого span в trace фиксировать два уровня данных: **атрибуты span** (что происходило) и **идентификаторы**, позволяющие пересечь trace с бизнес-данными. Данные делятся на общие для всех span и специфичные для этапа.

### 3.1. Общие атрибуты (все span)

| Данные | Зачем |
|---|---|
| `trace_id`, `span_id`, `parent_span_id` | Связь шагов в единый trace (сквозная видимость). |
| `service.name` (shop-api / crm-api / mes-api / rabbitmq-producer / rabbitmq-consumer / s3) | Где именно произошёл шаг — «кто» в цепочке. |
| `span.kind` (SERVER / CLIENT / PRODUCER / CONSUMER) | Направление взаимодействия: HTTP-обработчик, исходящий вызов, публикация/консьюм сообщения. |
| `timestamp` (start/end) + длительность | Хронология: когда заказ начал/закончил этап; где «потерялись» минуты/дни. |
| `status` (OK / ERROR) + `error.message` | На каком шаге «сломалось». |
| **`order_id`** | **Ключевой бизнес-идентификатор**: позволяет в UI найти trace конкретного заказа («где мой заказ?»). |
| `user_id` / `operator_id` / `seller_id` | Кто инициировал/обрабатывал (для разбора и SLA по операторам/продавцам). |
| `channel` (web B2C / api B2B) + `partner_id` (для B2B) | Источник заказа — B2C или конкретный B2B-партнёр. |
| `order_status` (текущий статус) | В какой статус заказ вошёл на этом шаге. |
| `env` (dev/release/prod) | Разделение окружений. |

### 3.2. Специфичные атрибуты по этапам (соответствуют статусам заказа)

| Этап (статус) | Сервис | Специфичные данные span |
|---|---|---|
| Создание заказа (`INITIATED` → `SUBMITTED`) | Shop API | `order_id`, `user_id`, `channel`, тип заказа (корзина/кастом), `item_ids` (без цен), `has_3d_file`. |
| Загрузка 3D-файла (`FILE_UPLOADED`) | Shop API → S3 | `s3_key` (только префикс/имя, **не содержимое**), `file_size`, `format` (GLB/OBJ/STL), `result` (ok/error). |
| Публикация «новый заказ» | CRM/MES (producer) | `queue`, `exchange`, `message_id`, `order_id`, `order_status`. |
| Приём сообщения из очереди | MES/CRM (consumer) | `queue`, `exchange`, `message_id`, `order_id`, `delivery_count` (сколько раз доставлялось — маркер проблем), `processing_started`. |
| Расчёт цены | MES API | `order_id`, `price_calculated` (факт, **не сумму в явном виде** — см. безопасность), `duration_ms` (длительность), `model_complexity` (число полигонов — объясняет 2–30 мин), `result` (success/failure/timeout). |
| Подтверждение (`MANUFACTURING_APPROVED`) | CRM API | `order_id`, `seller_id`, `approved_at`. |
| Работа оператора (`MANUFACTURING_STARTED` … `SHIPPED`) | MES API | `order_id`, `operator_id`, `operator_action` (взят/завершён/упакован/отправлен), `operator_time`. |
| Закрытие (`CLOSED`) | CRM API | `order_id`, `close_reason` (доставка/вручную), `carrier_id`. |
| DLQ-событие | RabbitMQ (consumer→DLQ) | `order_id`, `message_id`, `queue`, `reason`, `delivery_count` (маркер отравленного сообщения). |

### 3.3. Данные, которые **НЕ** должны попадать в трейсинг (гигиена и безопасность)

| Данные | Причина |
|---|---|
| Содержимое 3D-моделей, фото, PII клиента (ФИО, телефон, адрес) | Конфиденциальность: traces видны инженерам/поддержке; PII не нужна для диагностики и подпадает под требования к персональным данным. Только `user_id`-хеш. |
| Токены, ключи API, заголовки авторизации | Утечка через логи/traces = компрометация. |
| Полные тела запросов/ответов с чувствительными полями | Достаточно идентификаторов и статусов; тела — по отдельному решению (маскирование). |
| Точные деньги/цены в атрибутах span (кроме флага «price_calculated=true») | В trace фиксируем **факт** и длительность расчёта, а не сумму — минимизируем чувствительные данные. (Сумма — по запросу из БД по `order_id`.) |
| Случайные/высококардинальные значения в идентификаторах-метках | Держим атрибуты span (низкая кардинальность в trace), а не метрики с миллионами уникальных тегов (это уже зона метрик, задание 2). |

> **Принцип:** Trace должен ответить «что было с **этим** заказом и **где** он сейчас» при минимально необходимом наборе данных — без PII, без секретов, без содержимого 3D-моделей.

## 4. Предлагаемое решение

### 4.1. Выбор стека

| Компонент | Выбрать | Обоснование |
|---|---|---|
| **Протокол/стандарт** | **OpenTelemetry (OTel)** — OTLP-формат, W3C Trace Context (заголовки `traceparent`/`tracestate`) | Вендор-нейтральный стандарт; SDK есть для Java (Shop/CRM), C# (MES), RabbitMQ-агентов. Не привязывает к одному венدору и соответствует плану перехода на Kubernetes (автоматизация через OTel Collector / sidecar). |
| **Бэкенд трейсов (MVP)** | **Jaeger** (all-in-one, in-memory на dev, в prod — Elasticsearch/Cassandra или YC-Managed) | Прост в развёртывании через **jaeger-operator** в Kubernetes (готовые конфиги в репозитории), UI для поиска по `order_id`, API. MVP в к8s — из коробки. |
| **Коллектор** | **OpenTelemetry Collector** (Deployment в k8s, namespace `observability`) | Единая точка приёма OTLP от всех сервисов; позволяет в будущем менять бэкенд, добавлять маскирование, сэмплирование, экспорт в мониторинг (раздел 5) без переделки приложений. |
| **Инструментализация** | **Авто-инструментация** (Java agent / .NET SDK auto-instrumentation) + **ручные business-span** | HTTP-вызовы, DB-запросы — покрывает автоинструментация (min-code). А вот **RabbitMQ publish/consume, смена статуса заказа, расчёт цены** — это бизнес-события, их добавляем **ручными span** (span events / новые span-ы) с атрибутом `order_id`. |


### 4.2. Как реализуется сквозной трейс

1. **Вход заказа** (Shop API / CRM API / внешний API): создаётся корневой span (SERVER) с атрибутом `order_id`. Отсюда `trace_id` фиксируется на заказ.
2. **Пропагация через HTTP**: W3C-заголовки `traceparent`/`tracestate` передаются в каждом исходящем HTTP-вызове (SDK auto-instrumentation делает это сам).
3. **Пропагация через очередь (критично для нас)**: `trace_id` + `span_id` **помещаются в свойства сообщения RabbitMQ** (message headers / application-properties). При публикации — producer-span; при потреблении — consumer-span, привязанный к тому же `trace_id` (через `Baggage` / header). Так **один заказ = один trace** на всю жизнь, включая асинхронные «прыжки» между сервисами. Это закрывает слепые зоны R1/R2/R3.
4. **Долгие операции (расчёт цены, 2–30 мин)**: внутри расчёта ставим **промежуточные span-events** (checkpoints) — «модель получена из S3», «полигоны парсены», «цена вычислена». Если расчёт упал — trace покажет последний checkpoint, т.е. **точное место зависания** (R3).
5. **Долгая жизнь заказа (дни/недели)**: каждый сдвиг статуса (`MANUFACTURING_APPROVED`, `MANUFACTURING_STARTED`, … `SHIPPED`, `CLOSED`) — это **новый span в тот же trace**, привязанный по `order_id`. В Jaeger UI заказ — это **вещь со временем жизни**, а не один HTTP-запрос: видно «заказ создан 01.10, расчёт 01.10, подтверждён 03.10, в работе с 04.10, сейчас 31.10 и стоит в `MANUFACTURING_STARTED` 27 дней».

> Это ключевое отличие от «короткого» HTTP-трейсинга: у нас **traces живут неделями** и шьются по `order_id`, а не только по одному request-id.

## 5. Компромиссы: где трейсинг не принесёт пользы, невозможен или слишком дорог


### 5.1. Проприетарные системы (MES-движок расчёта)

Ядро MES (расчёт стоимости по полигонам) — купленный софт с исходным кодом, и его **внутренний** расчёт — не управляемый нами микро-сервис, а часть monolith'а MES API. Трейсинг видит **границу** этого компонента (вход: «начал расчёт», выход: «расчёт завершён», длительность, успех/ошибка), но **не видит internals** внутри расчёта, пока мы не вставим туда **ручные span-events** (чекпоинты).

- **Компромисс:** если доработка проприетарного кода «вставить чекпоинты в каждый шаг расчёта» дорога/рискна (сломает лицензионный поток), мы ограничиваемся **внешней границей** (начало/конец + длительность + ошибка). Тогда «завис на 30 минут в расчёте» будет видно, но «на каком именно подшаге полигонов» — нет.
- **Решение:** вставляем чекпоинты только на **критичные** подшаги (получение модели из S3, парсинг полигонов, итог расчёта) — это малый объём кода, а ценность максимальная. Глубокое instrumentation внутри ядерных алгоритмов — **отказываемся** (неоправданная цена).

### 5.2. Долгоживущие асинхронные процессы и «человеческие» паузы

Трейсинг отлично связывает **машинные** шаги (HTTP, очередь, БД). Но статусы `MANUFACTURING_STARTED`…`SHIPPED` включают **человеческое** время: оператор берёт заказ «в работу» через день, упаковывает через три.

- **Компромисс:** «пауза в 10 дней, потому что оператор не начал» — это **не сбой системы**, и трейсинг покажет её как «длинный промежуток», но **не объяснит причину** (а причина — в загрузке/плане оператора, а не в IT). Такие паузы нужно **интерпретировать отдельно** (раздел 5, мониторинг: алерт «заказ стоит в статусе > N дней» → это бизнес-решение, не IT-инцидент).
- Трейсинг **не заменяет** SLA-аналитику по людям: он фиксирует «когда», а «почему не начали» — из загрузки оператора/кредитов.

### 5.3. Сэмплирование и стоимость

100% сэмплирование всех запросов при росте +100 заказов/мес и B2B-нагрузке **дорого** (объём трейсов, retention, CPU на SDK).

- **Компромисс:** применяем **адаптивное сэмплирование**: 100% — **ошибки и DLQ** (их мы никогда не теряем), 10–20% — успешные запросы. Для **конкретных «проблемных» заказов** (жалоба клиента) — ручное «пробуждение» полного trace по `order_id`. То есть «вся история» есть у заказов, о которых уже известно, что они проблемные, а для фоновых — выборка. Это честный баланс стоимость/ценность.
- **Отказываемся** от 100% сэмплирования «на всякий случай» — неоправданная инфраструктурная цена.

### 5.4. Что трейсинг **не** решит (границы применимости)

| Проблема | Решит ли трейсинг |
|---|---|
| «Заказ завис в очереди, консьюмер упал» | **Да** — увидим отсутствие consumer-span / DLQ-span. |
| «Расчёт цены завис в середине» | **Да** (с чекпоинтами) — увидим последний пройденный подшаг. |
| «Оператор 10 дней не брал заказ в работу» | **Частично** — увидим паузу, но причину (человеческую) нет. |
| «Производство физически не успевает» | **Нет** — это capacity-проблема (метрики загрузки, задание 2), а не трейсинговая. |
| «Клиент ушёл с сайта, не оформив заказ» | **Нет** — это RUM/Web Vitals + Метрика (фронтенд), не бэкенд-трейсинг. |
| «Сбой в аутентификации» | **Нет** — по условию задачи auth вне покрытия. |
| «БД в целом деградирует (медленная на всём трафике)» | **Нет/частично** — это метрики БД (USE); трейсинг покажет лишь «доли» запросов длиннее. |

**Вывод:** трейсинг — инструмент **диагностики конкретного заказа/запроса** и **сквозной видимости асинхронной цепочки**. Он дополняет (а не заменяет) мониторинг (агрегаты, saturation) и RUM (фронтенд). Внедрять его «вместо» других слоёв — ошибка.

### 5.5. Стоимость и риск внедрения

- **Самый дорогой/рisky элемент — доработка собственной RabbitMQ-интеграции** (F3): писать/читать `traceparent` в заголовки сообщений. Это **единая точка** закрытия главных слепых зон (R1–R3), поэтому **не отказываемся**, но делаем её **осторожно**: сначала в dev/release, с флагом (feature toggle), без изменения схемы очереди, чтобы не «сломать» живую интеграцию. Риск: несовместимость старых/новых сообщений при деплое — митигируем версионированием заголовка и дефолтным «новый trace» при отсутствии.
- **Не внедряем** отдельный тяжёлый commercial-трейсинг (например, Datadog/NewRelic APM) — при нашем стеке и плане перехода на k8s **OTel + Jaeger** дешевле и вендор-нейтральны. Переключение на commercial-бэкенд сохранится как опция (OTel это позволяет), но **не оправдано** на текущем объёме.

## 6. Безопасность: защита системы трейсинга

Трейсинг-слой — это **новая** поверхность с доступом к идентификаторам заказов, операторов, партнёров и временным линиям (само по себе — чувствительная бизнес-информация). Определяем меры против несанкционированного доступа **внутри** и **снаружи**.

### 6.1. Что защищаем

| Ассет | Риск при утечке |
|---|---|
| **Трейсы (Jaeger/Cassandra)** — содержат `order_id`, `operator_id`, `partner_id`, длительности, статусы | Раскрытие внутренней работы, SLA-деградации, PII-смежные данные; конкурент разглядит наши узкие места. |
| **OTel Collector** — единая точка приёма | Перехват/подмена метрик (ввод ложных данных, DDoS на приём). |
| **UI/Query API Jaeger** (16686) | Чтение всех traces; в dev — вообще без аутентификации (опасно в prod). |
| **Данные в spanх** | PII, суммы, содержимое 3D-моделей — попадание в trace. |

### 6.2. Меры **внутри** компании

1. **Аутентификация доступа к Jaeger UI / Query API.** Внедряем **SSO / централизованную аутентификацию** (корпоративная IdP) — зайти в систему смогут **только сотрудники компании с актуальной учётной записью**. В dev-окружении допустим базовый доступ (внутри кластера, без наружу), в release/prod — **обязательная** IdP-аутентификация.
2. **Авторизация по ролям (RBAC).** Доступ к чтению traces — только с ролью **«Поддержка» / «Дежурный» / «Архитектор» / «DevOps»**. Продавцы/операторы **без** прямого доступа к Jaeger (им нужен «заказ → trace» через свой UI поддержки, см. 6.4). Администраторы (PM, тимлид, менеджеры) — доступ «только чтение» к traces, которые их касаются (по `partner_id`/`channel`).
3. **Сетевая сегментация.** OTel Collector и Jaeger — в **отдельном namespace `observability`** в выделенной подсети **только внутренней** сети. **Никаких** inbound-портов наружу (prod). Query/UI — **только** через внутренний reverse-proxy с SSO (Service internal / Ingress с authn), **не** exposed наружу.
4. **mTLS между сервисами и Collector.** Сервисы шлют OTLP в Collector по **мTLS** (сертификаты через cert-manager в k8s) — защита от перехвата/подмены метрик внутри сети. В dev (in-memory) mTLS опционален; в prod — обязателен.
5. **Маскирование данных на входе (Data Masking) в OTel Collector.** Конфигурируем **processors/masking**: исключить/заменить PII-атрибуты (ФИО, телефон, email), токены, ключи API — **до** записи в хранилище. Дополнительно **запрет** вносить содержимое 3D-моделей и суммы (см. 3.3) — код-рвью на наличие таких атрибутов.
6. **Retention и удаление.** Хранение traces — **30 дней** (prod), агрегированные метрики — 12 мес. По истечении — **авто-удаление**. Это снижает объём и поверхность утечки.
7. **Аудит доступа.** Логируем, **кто** открывал **какие** traces (по `order_id`) — для расследований и контроля «кто когда смотрел чужой заказ».

### 6.3. Меры **снаружи** (если требуется наружный доступ)

Базовый сценарий — **внешнего** доступа к Jaeger **нет**. Если возникнет (например, B2B-партнёру показать статус по `order_id`):

1. **Не открываем** Jaeger наружу. Вместо этого — **отдельный публичный статус-эндпоинт** (в CRM/Shop API) вида `GET /public/orders/{order_id}/status`, который возвращает **только обезличенный** статус и время, а **не** внутренний trace. Это минимизирует раскрытие.
2. Для редких случаев совместного расследования с партнёром — **временный** выдача **ссылки** на конкретный трейс через reverse-proxy с **время ограниченным токеном** (ссылка с TTL) и ограничением на **один** `order_id`. Никогда — общий доступ к Query API.
3. **WAF / rate-limiting** на любой наружный эндпоинт, связанный с observability, против сканеров/перегрузки.



## 7. Автоматический мониторинг прохождения заказа и алертинг (дополнительное задание)

Трейсинг — **пассивный** журнал: он отвечает на вопрос, когда его уже открыли. Чтобы **до жалобы клиента** узнавать о «зависших» заказах, строим поверх данных трейсинга **автоматический мониторинг + алертинг**.

### 7.1. Подход: «ожидание этапа» (SLI из traces)

Каждый «здоровый» заказ проходит предсказуемую последовательность событий (span) с реалистичными временными рамками. Мониторинг = проверка, **прошёл ли** заказ ожидаемый этап за ожидаемое время.

**Источник данных:** из traces (через атрибуты span и status) мы извлекаем для каждого `order_id`:
- **последний пройденный этап** (какой статус/span есть в trace);
- **время** последнего события;
- **ошибки** (span с `status=ERROR`, DLQ-span).

Это превращает traces в **событийный конвейер**, по которому считается «возраст заказа на этапе» — готовый вход для алертов.

### 7.2. Компоненты

| Компонент | Роль |
|---|---|
| **Order Lifecycle Watcher** (новый, «зелёный») | Периодически (каждые 1–5 мин) читает свежие span по `order_id` (из Jaeger Query API или — лучше — из общего потока/хранилища), агрегирует «последний этап + время + ошибка» на заказ. Публикует **бизнес-метрики** (Prometheus-формат): `order_age_in_stage_seconds`, `order_stage_errors_total`, `order_stuck_total{stage}`. |
| **VictoriaMetrics / Prometheus** (совпадает с заданием 2) | Хранит бизнес-метрики от Watcher. Единый TSDB с метриками задания 2. |
| **Prometheus rules** (новый, «зелёный») | Пороговые правила: «заказ в этапе X > T», «span-ошибка на этапе», «DLQ-span», «новый статус не появился за T». |
| **Alertmanager** (совпадает с заданием 2) | Роутинг уведомлений: Telegram + тикет; critical — звонок дежурному. |
| **Grafana** (совпадает с заданием 2) | Дашборд «Order pipeline» (светофор по этапам + age) + «Stuck orders» (список конкретных `order_id` со ссылкой на trace). |

> **Связь с трейсингом:** Watcher **читает данные трейсинга** (span по `order_id`) — это и есть «мониторинг, полученный из данных трейсинга». Ссылка на конкретный **трейс** кладётся в каждый алерт — дежурный открывает trace в один клик и видит **полную историю** зависшего заказа.

### 7.3. Алерты (из данных трейсинга)

| # | Алерт (условие, из traces) | Уровень | Почему важно |
|---|---|---|---|
| **A1** | span-ошибка (`status=ERROR`) на **любом** этапе обработки заказа | Critical | Заказ уже сломан; требуется немедленное действие. |
| **A2** | **DLQ-span** (сообщение ушло в dead-letter) | Critical | Заказ «потерялся» из рабочего потока (R2). |
| **A3** | Нет consumer-span после producer-span > 5 мин (сообщение «зависло» в очереди) | Critical | Консьюмер упал / не потребляет (R1). |
| **A4** | Расчёт цены: нет span-event «price_calculated» > 30 мин | Warning → Critical (60 мин) | Расчёт завис (R3). 30 мин — известный максимум. |
| **A5** | Заказ в рабочем статусе (MANUFACTURING_*) без движения > N дней | Warning | Человеческая/бизнес-пауза (см. 5.2) — эскалация PM, не IT-инцидент. |
| **A6** | `order_id` из жалобы/поддержки — запрос «дай полный trace» | Инфо | Быстрый ответ клиенту/партнёру (мотивация 2.2). |

### 7.4. Обновлённая диаграмма (зелёным)

На **итоговой диаграмме** (раздел 4.5) поверх красных (трейсинг) добавлены **зелёные** компоненты и связи:

- **Order Lifecycle Watcher** (зелёный контейнер) — читает **span/треды** из Jaeger (связь Watcher → Jaeger, зелёная).
- **Watcher → VictoriaMetrics** (зелёная): публикация бизнес-метрик по `order_id`.
- **VictoriaMetrics → Prometheus rules / Alertmanager** (зелёные): правила порогов и роутинг алертов.
- **Alertmanager → Telegram/дежурный** (зелёная): уведомление с **ссылкой на trace**.
- **Grafana дашборд «Stuck orders»** (зелёная): список конкретных зависших заказов со ссылками на traces.

### 7.5. Что это даёт 

- **MTTD «зависшего» заказа** — с «месяца (жалоба)» до **минут** (алерты A1–A4). Реализует метрику **M1**.
- Каждое «потерянное» состояние заказа становится **автоматическим** алертом, а не ручным поиском. Реализует **M3**.
- Дежурный получает **готовый trace** в алерте → **MTTR** в разы ниже (реализует **M2**).
- Это превращает пассивный трейсинг в **активного сторожа** конвейера заказов.

## 8. Критерии успеха (как поймём, что трейсинг окупился)

- Через 2 недели: **ни одного «зависшего» заказа, о котором узнали только из жалобы клиента** (все — по алертам A1–A4).
- **MTTD** зависшего заказа: ≤ 15 минут (было: неделя/месяц).
- **MTTR** разбора: открытие одного трейса вместо ручного поиска по 5 системам (цель: ≤ 10 минут до идентификации этапа/причины).
- **Coverage**: ≥ 95% заказов имеют полный сквозной trace (M4).
- **M5**: снижение числа потерянных заказов/контрактов в месяц на фоне роста +100 заказов/мес.
- B2B-партнёрам — готовый ответ «на каком этапе ваш заказ» со ссылкой на trace (через обезличенный статус-эндпоинт).
