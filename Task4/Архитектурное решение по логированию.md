## 1. Анализ: какие логи собирать

Сейчас проблемы разбираются «со слов клиента»: менеджер пересказывает жалобу, разработчики в лучшем случае лезут на инстансы и вручную читают разрозненные stdout/файлы логов, не имеющие ни общей структуры, ни временной привязки к конкретному заказу. Это дорого по времени (часы на один разбор) и ненадёжно (логи на EC2-инстансах уходят при рестарте/деплое, а деплои здесь ручные и частые).

Вывод: нужен **центральный журнал событий**, в который каждое приложение пишет **структурированные** (JSON) записи с обязательной связкой к заказу и к трейсу. Ниже — что именно логировать, из каких систем, на каких уровнях.

### 1.1. Цепочка прохождения заказа (напоминание)

```
[Клиент]  -> Интернет-магазин (Vue) -> Shop API (Spring Boot) -> Shop DB
[Партнёр] -> MES API (C#, внешний API)                          \
                                                      [Продавец] -> CRM (Vue) -> CRM API (Spring Boot)
                                                                                          |
                                                                     3D-файл -> S3-хранилище
                                                                             v
                                                                  RabbitMQ (очереди/топики)
                                                                             v
                                                             MES API (C#) -> MES DB -> [Оператор]
```

Заказ проходит **через 3 приложения + очередь + 2 БД + S3**. Сегодня ни одно из этих звеньев не оставляет сквозного, структурированного, персистентного следа.

### 1.2. Системы, из которых требуется сбор логов (отмечены на схеме)

Собираем логи со всех точек, через которые проходит заказ и где он реально «ломается» (зоны риска совпадают с зонами из задания 3 по трейсингу):

| # | Система | Почему именно она | Приоритет |
|---|---|---|---|
| **L1** | **MES API (C#)** | Узкое место и главный источник сбоев: приём заказа из очереди, **расчёт цены 2–30 мин** (упадение/зависание в середине), действия оператора. Здесь больше всего «нестандартных ситуаций». | **1 (сначала)** |
| **L2** | **RabbitMQ (интеграция CRM↔MES)** | Точка, где заказы **буквально теряются**: публикация/консьюм, повторы, **dead-letter**. Каждое сообщение в DLQ = потенциально потерянный заказ. Интеграция — собственная, логировать просто. | **1 (сначала)** |
| **L3** | **Shop API (Spring Boot)** | Точка входа B2C-заказа: создание заказа, загрузка 3D-файла, оформление. Без этих логов не понятно, «родился ли» заказ и с чем он пришёл в MES. | **1–2** |
| **L4** | **CRM API (Spring Boot)** | Точка подтверждения (`MANUFACTURING_APPROVED`) и закрытия (`CLOSED`); приём заказов из очереди (B2B) и передача в MES. «Шлюз» между клиентом и производством. | **2** |
| **L5** | **S3-хранилище 3D-файлов** | Загрузка/чтение моделей: ошибки put/get блокируют `FILE_UPLOADED` и расчёт. Доступны access-логи хранилища. | **2** |
| **L6** | **Shop DB / MES DB (PostgreSQL)** | Медленные/ошибочные запросы (причина медленного дашборда). Собираем **селективно** (slow log + ошибки), не все запросы — иначе PII-сквозняк и шум. | **3 (фаза 2)** |
| **L7** | **Фронтенды (Vue, React)** | Console-ошибки, падение загрузки страниц, RUM. Не является частью цепочки создания заказа — **фаза 2**, отдельно (см. 1.4). | **3 (фаза 2)** |


На [схеме с логированием](c4/alexandrite_c4_logging.drawio) системы L1–L5 выделены **синим пунктирным прямоугольником** — «логирование включено», новые компоненты (Collector, OpenSearch, Grafana, Alertmanager) — **синим цветом**.

### 1.3. Список необходимых логов уровня INFO

Уровень **INFO** — это «журнал жизни заказа»: нормальные, ожидаемые бизнес-события, по которым можно восстановить хронологию конкретного заказа без единого сбоя. Каждая запись — **структурированный JSON** с общими полями (см. 1.3.1) + специфичными (см. 1.3.2).

#### 1.3.1. Общие поля каждой записи INFO (обязательный каркас)

| Поле | Пример | Зачем |
|---|---|---|
| `timestamp` (ISO-8601, ms) | `2026-10-03T12:34:56.789Z` | Когда событие произошло. |
| `level` | `INFO` | Уровень. |
| `service.name` | `mes-api` / `shop-api` / `crm-api` / `rabbitmq` | Кто записал — «кто» в цепочке. |
| `env` | `prod` / `release` / `dev` | Разделение окружений. |
| **`trace_id`** / `span_id` | `4bf92f…` | **Связка с трейсингом (задание 3):** по нему лог и трейс конкретного заказа — это одно и то же. Ключевое требование. |
| `event.type` | `ORDER_STATUS_CHANGED`, `PRICE_CALC_STARTED` | Тип бизнес-события (фильтр в поиске). |
| **`order_id`** | `ORD-100234` | **Ключевой бизнес-идентификатор:** «покажи всё про этот заказ». |
| `actor` (user_id / operator_id / seller_id / partner_id) | `u_8842`, `op_17`, `partner_03` | Кто инициировал/обрабатывал. Для PII — только хеш (см. 3.5). |
| `channel` | `web` / `api` | B2C или B2B (для B2B + `partner_id`). |


#### 1.3.2. Специфичные INFO-события по этапам (соответствуют статусам заказа)

| Этап / событие | Сервис | INFO-поля сверх общих |
|---|---|---|
| **Создание заказа** (`INITIATED`) | Shop API | `order_id`, `user_id`, `channel`, `order_type` (корзина/кастом), `has_3d_file`, `item_count` (без цен/PII). |
| **Загрузка 3D-файла** (`FILE_UPLOADED`) | Shop API → S3 | `order_id`, `s3_key` (префикс/имя, **не содержимое**), `file_size_bytes`, `format` (GLB/OBJ/STL), `result=ok`. |
| **Оформление** (`SUBMITTED`) | Shop API | `order_id`, `user_id`, `submit_channel`. |
| **Публикация «новый заказ» в очередь** | CRM/MES (producer) | `order_id`, `exchange`, `queue`, `message_id`, `to_status`. |
| **Приём сообщения из очереди** | MES/CRM (consumer) | `order_id`, `queue`, `message_id`, `delivery_count` (сколько раз доставлялось — маркер повторов), `processing_started=true`. |
| **Начало расчёта цены** | MES API | `order_id`, `model_polygons` (число полигонов — объясняет длительность), `calc_queue_position`. |
| **Окончание расчёта цены** (`PRICE_CALCULATED`) | MES API | `order_id`, `duration_ms`, `result=success` (**факт, не сумму** — см. 3.5), `to_status`. |
| **Подтверждение** (`MANUFACTURING_APPROVED`) | CRM API | `order_id`, `seller_id`, `approved_at`. |
| **Взял в работу** (`MANUFACTURING_STARTED`) | MES API | `order_id`, `operator_id`, `assigned_at`. |
| **Готово к упаковке** (`MANUFACTURING_COMPLETED`) | MES API | `order_id`, `operator_id`, `completed_at`. |
| **Упаковка** (`PACKAGING`) | MES API | `order_id`, `operator_id`. |
| **Отправлен** (`SHIPPED`) | MES API | `order_id`, `carrier_id`, `shipped_at`. |
| **Закрыт** (`CLOSED`) | CRM API | `order_id`, `close_reason` (доставка/вручную), `carrier_id`. |


#### 1.3.3. Что НЕ попадает в INFO-логи (гигиена)

| Данные | Причина |
|---|---|
| Содержимое 3D-моделей, фото | Конфиденциально; огромно; не нужно для диагностики. Только метаданные (`s3_key`, `file_size`, `format`). |
| PII клиента (ФИО, телефон, email, адрес) | Только `user_id`-хеш. ПЕРЕХОДЯТ под требования к персональным данным (152-ФЗ). |
| Токены, ключи API, заголовки авторизации | Утечка = компрометация. |
| Суммы/цены в явном виде | В INFO фиксируем **факт** `price_calculated=true` + длительность; сумму — по запросу из БД по `order_id`. |

### 1.4. Другие уровни логирования и обстоятельства

INFO — не единственный уровень. Политика уровней:

| Уровень | Когда писать | Примеры в нашей системе |
|---|---|---|
| **DEBUG** | Детали для отладки; **включать только в dev/release**, в prod — отключён (шум+PII-риск). Не в централизованное хранилище по умолчанию. | Выходные значения методов, распарсенные поля 3D-файла, тело запроса API (обезличенное). |
| **INFO** | Нормальные бизнес-события («жизнь заказа») и ключевые технические успехи. | Всё из 1.3. |
| **WARN** | **Восстановимая** аномалия: система справится, но требует внимания. Пороги — те же, что в задании 2 (насыщенность). | Повтор доставки сообщения (`delivery_count>1`); расчёт цены идёт > 15 мин (ближе к потолку 30); очередь растёт (глубина > порога); медленный запрос дашборда > 2 с; исчерпание пула соединений > 70%; retry операции S3. |
| **ERROR** | **Сбой**, который требует реакции; заказ/операция не выполнен. Тихо не проходит — идёт в алерт (раздел 4). | Ошибка расчёта цены (исключение, `result=failure`); **сообщение в DLQ**; 5xx на API (особенно B2B); таймаут чтения/записи БД; не удалось загрузить 3D-файл (`FILE_UPLOADED` не достигнут); несерилизуемое/битое сообщение из очереди. |
| **FATAL** *(фаза 2, опц.)* | Падение процесса/консьюмера целиком. | OOM, crash-консьюмера MES (связать с алертом «0 консьюмеров»). |

**Правило корреляции:** и WARN, и ERROR **обязательно** несут тот же набор полей, что и INFO (`trace_id`, `order_id`, `service.name`, `env`) + `error.type`/`error.message` (обезличенное) + `stack_trace` (для ERROR, маскированный). Так по одному `order_id`/`trace_id` видна **вся** история, включая сбой.

## 2. Мотивация

### 2.1. Почему системе нужно логирование (и почему «со слов клиента» не работает)

Сегодня диагностика проблем — это **расследование по воспоминаниям**:

1. **Нет ответа «что произошло с этим заказом».** Клиент говорит «мой заказ пропал», а разработчики не могут показать цепочку: создан ли он, дошёл ли в очередь, был ли потреблён, начат ли расчёт, где упал. Логи на трёх инстансах EC2 разрозненны, часто неструктурированы (строки в stdout), привязаны к времени «на глаз», а после ручного деплоя/рестарта **части логов уже нет**.
2. **Разбор занимает часы и блокирует разработчика.** Для одной жалобы нужно руками логироваться на 3 EC2 + 2 БД + RabbitMQ, искать по именам файлов и времени, сопоставлять вручную. Это дорогая работа senior-инженера, которая не масштабируется.
3. **Жалоба приходит слишком поздно.** К моменту, когда клиент звонит, заказ уже «сгорел» (месяцы). Мы не знаем, **когда именно** он перестал двигаться — значит, не можем ни предупредить, ни быстро восстановить.
4. **Нет данных для анализа трендов.** «Участились проблемы» — это ощущение. Без центрального журнала нельзя ответить: ошибки выросли после деплоя X? Только по конкретному партнёру? На конкретном этапе?
5. **Поддержка перегружена.** Операторы и менеджеры переспрашивают клиентов, тикеты уходят разработчикам «на разберите, что случилось» — и там снова ручной поиск.

Логирование + централизованный анализ превращают этот процесс в **поиск по `order_id`** в одном месте: за секунды видно полную хронологию заказа по всем системам, связанную с трейсом (задание 3) и метриками (задание 2).

### 2.2. Что это даст компании

1. **Сокращение времени разбора (MTTR)** с часов до минут: по `order_id` — вся история заказа по всем сервисам в одном поиске, переход в трейс в один клик.
2. **Ответ клиенту/партнёру фактами.** Менеджер/поддержка открывает заказ и говорит: «создан 01.10 12:00, в очереди 12:02, расчёт 12:05–12:08, подтверждён 02.10, в работе с 03.10» — вместо «мы проверим». Это прямо влияет на сохранение B2B-контрактов.
3. **Обнаружение проблем до жалобы клиента.** ERROR/WARN-логи + алерты (раздел 4) по DLQ, ошибке расчёта, 5xx на B2B-API — узнаём о потере заказа в минуты, а не через месяц.
4. **Данные для анализа инцидентов и релизов.** «Выросли ли ошибки после деплоя» — один график. Это снижает риск ручных деплоев (P10 из задания 1) и ускоряет поиск регрессий.
5. **Разгрузка поддержки и разработчиков.** Стандартные вопросы («где мой заказ») закрываются поиском, а не челн-хопом.

### 2.3. Метрики решения (3–5), на которые повлияет внедрение логирования

| # | Метрика (тип) | Как меняется | Как измерить |
|---|---|---|---|
| **М1** | **MTTR разбора «потерянного/зависшего» заказа** (техническая, минуты) | С «часов (ручной поиск по 5 системам, часть логов уже стёрта)» до **минут** (поиск по `order_id` + переход в трейс). | Время от открытия тикета до идентификации этапа и причины; фиксировать в тикетах. Сравнить «до/после» за месяц. |
| **М2** | **MTTD — время обнаружения сбоя до жалобы клиента** (бизнес KPI, часы) | С «недели/месяца (по жалобе)» до **минут** (алерт по ERROR/DLQ/5xx, раздел 4). | Разница: когда заказ/запрос сломался (по логам) vs когда команда получила алерт. |
| **М3** | **Доля заказов с полным центральным логом (coverage)** (качество, %) | Растёт к **100%**: у каждого заказа есть структурированный лог по всем этапам, включая сбой. Низкий coverage = есть «слепые» звенья. | (заказы с полным набором INFO-событий по конвейеру) / (все заказы). Ежедневный отчёт из OpenSearch. |
| **М4** | **Среднее время ответа поддержки/продаж на «где мой заказ»** (бизнес, минуты) | С «часов/дня (ручной поиск)» до **минут** (готовый отчёт по `order_id`). Прямая разгрузка поддержки. | Замер по тикетам поддержки до/после. |
| **М5** | **Число «сгоревших» заказов/контрактов в месяц** (бизнес KPI, шт.) | Снижается: раннее обнаружение (М2) + быстрый разбор (М1) → заказы восстанавливаются до «сгорания». | Бизнес-показатель от продаж/PM; месячный тренд. |


### 2.4. Приоритет: какие системы настроить логирование (и трейсинг) в первую очередь и почему

Команда **не сможет** сделать логирование и трейсинг всех систем единовременно (9 человек, 2-недельные спринты, живое приложение с ростом нагрузки). Поэтому — приоритизация по принципу **«сначала там, где заказы реально теряются и где дороже всего ошибка»**:

| Волна | Системы | Почему именно сейчас |
|---|---|---|
| **Волна 1 (1–2 спринта, P0)** | **MES API (C#)** + **RabbitMQ-интеграция** | Это **узкое место и точка потери**: расчёт цены 2–30 мин (самые долгие операции, максимум сбоев: падение/зависание в середине) + очередь/DLQ (там заказы буквально исчезают). Отсюда исходит основная часть жалоб S1/S3. Логирование здесь закрывает больше всего боли за минимальные усилия (интеграция — наша, MES API — управляемый нами C#). |
| **Волна 2 (2–3 спринта, P1)** | **Shop API (Spring Boot)** + **CRM API (Spring Boot)** | Точка входа (B2C: создание, загрузка файла, оформление) и «шлюз подтверждения/закрытия» (CRM). Без них лог заказа неполный: видно середину конвейера, но не «родился ли» заказ и не «закрыт ли». Java-агенты дают быстрый старт. |
| **Волна 3 (фаза 2, P2)** | **S3 access-логи** + **Shop DB / MES DB (slow log, ошибки)** | Диагностика «почему файл не читается» и «какой запрос тормозит дашборд». Менее критично для «потерянных заказов», важно для производительности (S4). |
| **Волна 4 (фаза 2, P2)** | **Фронтенды (Vue, React)** — console-ошибки, RUM | UX-проблемы; не являются частью цепочки создания заказа. Добавляются отдельно (Mетрика/otlp-web) после стабилизации бэкенд-лога. |

> **Обоснование «MES + очередь первыми»:** (1) максимальная доля «потерянных» заказов приходится именно на расчёт и доставку через очередь; (2) это зоны, которые **мы** контролируем (MES API — купленный софт с исходниками, интеграция — наша), поэтому логирование реализуемо дёшево и быстро; (3) лог + трейс именно здесь дают прямой ответ на главный вопрос «где и почему завис заказ». Сначала закрываем «потерю», потом «полноту».

> **Связка с трейсингом:** волны логирования совпадают с волнами трейсинга задания 3. На волне 1 включаем и то, и другое одновременно (один OTel Collector, один `trace_id`) — это дешевле, чем дважды трогать MES API и очередь.

## 3. Предлагаемое решение

### 3.1. Выбор стека

Принцип: **один OTel-слой** (задания 2/3) собирает и метрики, и трейсы, и логи; логи — в поисковое хранилище, которое умеет full-text поиск, алерты и аномалии. Всё в Yandex Cloud, в namespace `observability` в Kubernetes (в рамках плана перехода).

| Компонент | Выбрать | Обоснование |
|---|---|---|
| **Формат логов** | **Структурированный JSON** (Logback `logstash-encoder` / `json-template` для Java; **Serilog → JSON** для C#) | Единый формат, который парсится любой системой; по полям (`order_id`, `trace_id`, `level`) — быстрый поиск и корреляция. Текстовые строки в stdout **запрещены** в prod. |
| **Внедрение в приложения** | **OpenTelemetry Logs SDK** (Java, .NET) — лог-записи получают `trace_id`/`span_id` автоматически из контекста + **appender-экспорт** (file/stdout → agent) | Те же SDK, что для трейсинга (задание 3). `trace_id` в лог — «бесплатно» из контекста. Минимум нового кода. |
| **Сбор/аггрегация** | **OpenTelemetry Collector** (реализуется как daemonset/sidecar + Deployment в k8s `observability`) — принимает OTLP **logs** (4317/4318) + file-tail, шлёт в хранилище | **Воспользуемся тем же Collector'ом из задания 3** — один и тот же приёмник для spans и logs. Единая точка, единый mTLS, единое маскирование. |
| **Хранилище + поиск + алерты + аномалии** | **OpenSearch** (self-hosted в k8s / либо управляемый Elasticsearch/OpenSearch в YC) | Apache-2.0 (см. раздел 5), full-text поиск, индексы на систему, **built-in Alerting + Anomaly Detection** (раздел 4), интеграция с Grafana. Альтернатива для MVP — **Loki** (дешевле, нативно в Grafana, но слабее поиск/аномалии) — см. 5. |
| **Визуализация / лог-эксплорер** | **Grafana** (из задания 2) + **OpenSearch Dashboards** | Grafana уже есть (метрики/трейсы). Лог-эксплорер — в Grafana (OpenSearch datasource) + в OpenSearch Dashboards для полноты. |
| **Алертинг по логам** | **OpenSearch Alerting** → **Alertmanager** (из задания 2) → Telegram/тикет | Единый Alertmanager = единая маршрутизация алертов по логам, метрикам и трейсам. |

> **Почему не «просто tail-файлы на инстансах»:** инстансы — по одному, деплои ручные, логи теряются при рестарте/миграции. Централизованный сбор + персистентное хранилище — обязательное условие для «разбор по заказу».

### 3.2. Как реализуется сбор: путь одной записи лога

```
Приложение (Java/C#) 
  -> Logback/Serilog (JSON, поля: level, event.type, order_id, trace_id, env, ...)
  -> OTel Logs SDK (добавляет trace_id/span_id из контекста)
  -> OTLP/HTTP (mTLS)  ->  OpenTelemetry Collector (namespace observability)
       [маскирование PII/секретов, сэмплирование, батчинг]
  -> OpenSearch (индекс: alex-logs-{service}-{YYYY.MM}, ILM/rollover)
  -> Grafana (Log Explorer) / OpenSearch Dashboards
  -> OpenSearch Alerting -> Alertmanager -> Telegram/дежурный/тикет
```

Ключевые свойства:
1. **Корреляция:** `trace_id` в лог из контекста (задание 3) → «лог ↔ трейс одного заказа» в один клик.
2. **Потеря данных минимальна:** батчинг в Collector + персистентный буфер; падение приложения не теряет уже переданные логи.
3. **Асинхронность:** логирование не блокирует обработку заказа (аппендер асинхронный, очередь в Collector).
4. **Отказоустойчивость:** Collector — Deployment с репликами; при сбое хранилища — локальный буфер (backpressure) с ограничением по времени.

### 3.5. Политика безопасности (чувствительные данные, доступ)

Логи — **новая поверхность утечки**: в них есть `order_id`, `operator_id`, `partner_id`, `s3_key`, временные линии, ошибки. Определяем работу с чувствительными данными и доступ.

**1. Работа с чувствительными данными (Data Masking / DLP в логах):**

| Данные | Политика |
|---|---|
| **PII клиента** (ФИО, телефон, email, адрес) | **Не логировать** в явном виде. Только `user_id` (внутренний ID) или **необратимый хеш**. Masking в Collector (processor) как вторая линия защиты — до записи в OpenSearch. |
| **Секреты** (токены, ключи API, пароли, заголовки авторизации, JWT) | **Категорически не логировать.** Black-list ключей в логгере + маскирование в Collector. Запрет на запись заголовка `Authorization`. |
| **Содержимое 3D-моделей / тела запросов с данными** | Не логировать содержимое. Только метаданные (`s3_key`, `file_size`, `format`, `polygons`). |
| **Суммы/цены** | В логе — **факт** `price_calculated=true` + `duration_ms`, не сумму. Сумма — по запросу из БД по `order_id`. |
| **Полные тела запросов/ответов API** | По умолчанию **не** в prod-лог (шум + PII-риск). Только в dev, и только обезличенное; в prod — по отдельному решению на время расследования. |
| **Stack trace в ERROR** | Логируем, но **маскируем** (удаляем аргументы, содержащие PII/секреты); ограниченный размер. |

**2. Доступ к логам (RBAC):**

| Роль | Доступ |
|---|---|
| **Поддержка / Дежурный** (тимлид, Java, C#, DevOps) | Чтение логов (Grafana/OS Dashboards) по `order_id`/`trace_id`/`service`. Основной пользователь. |
| **Разработчики** (Java, C#, фронтенд) | Чтение логов своего сервиса + dev/release окружений. |
| **Архитектор** | Чтение всех логов всех окружений + настройка (индексы, маскирование). |
| **Администраторы (PM, тимлид, менеджеры)** | **Ограниченный** доступ: только «заказ → отчёт» (статус/хронология) через поддержку, **не** прямой доступ к сырым логам (минимизируем раскрытие PII-смежных данных). |
| **Продавцы / операторы** | **Без** прямого доступа к логам. Им нужен статус заказа — через CRM/MES UI, а не через OpenSearch. |
| **Системы** (Collector, Alerting) | Отдельные сервисные аккаунты с минимальными правами (Collector — запись в индексы; Alerting — чтение). |

**3. Технические меры защиты:**
- **Аутентификация**: доступ к Grafana/OS Dashboards — только через **корпоративную IdP (SSO)**; зайти могут только сотрудники с актуальной учётной записью.
- **Сетевая сегментация**: OpenSearch/Collector — в `observability` namespace, **внутренняя** подсеть, **никаких inbound наружу** (prod). UI — только через reverse-proxy с SSO, не exposed.
- **mTLS** между сервисами и Collector (защита от перехвата/подмены логов в сети) — те же сертификаты, что в задании 3.
- **Шифрование**: шифрование **at rest** (OpenSearch — AES-шифрование данных на диске, ключи в YC KMS) и **in transit** (TLS/mTLS).
- **Аудит доступа**: логируем, **кто** открывал **какие** логи (по `order_id`) — для расследований и контроля.
- **Окружения**: dev — упрощённый доступ (внутри кластера); release/prod — обязательная SSO + RBAC.

### 3.6. Политика хранения (индексы, сроки, размер)

**1. Разделение по индексу на систему** (обязательное требование задачи):

| Индекс | Источник | Почему отдельный |
|---|---|---|
| `alex-logs-mes-api-{YYYY.MM}` | MES API | Самый «шумный» (расчёты, операторы), отдельный ILM и поиск. |
| `alex-logs-shop-api-{YYYY.MM}` | Shop API | B2C-вход, другой профиль/объём. |
| `alex-logs-crm-api-{YYYY.MM}` | CRM API | Подтверждения/закрытие, приём из очереди. |
| `alex-logs-rabbitmq-{YYYY.MM}` | Интеграция (publish/consume/DLQ) | Критичный канал; отдельный, чтобы DLQ-события не терялись в потоке. |
| `alex-logs-s3-{YYYY.MM}` | S3 access-логи (фаза 2) | Access-логи — особый формат. |
| `alex-logs-db-{YYYY.MM}` | БД slow/error (фаза 2) | Селективно; отдельный из-за PII-риска в текстах запросов. |


**2. Сроки хранения (retention по ILM):**

| Тип данных | Срок | Обоснование |
|---|---|---|
| **ERROR / WARN / DLQ-события** (все сервисы) | **90 дней** (горячий) | Редкие, критичные для разборов; держим дольше для ретроспективы инцидентов и релизов. |
| **INFO-логи** | **30 дней** (горячий) | Достаточно для типового разбора «заказ» (живёт до 3 недель SLA + запас). |
| **Агрегированные / cold** (по итогам, по `order_id`-ключевым) | **12 месяцев** (warm/cold, сжатие) | Для трендов, отчётности SLA перед B2B, аудита. |
| **После 12 мес** | **Авто-удаление** | Снижение объёма и поверхности утечки; юридически достаточно 12 мес (кроме специфичных требований). |

> **Специальный кейс:** заказы, о которых **известно, что проблемные** (жалоба/алерт), — **помечаем** (tag `keep=incident`), и их логи **не удаляем** до закрытия инцидента (даже за пределами 30 дней) — для полного разбора.

**3. Размер (оценка):**

- Ориентир: ~2–5 KB на INFO-событие (JSON с полями), ~10–30 KB на ERROR со stack trace.
- Оценка потока (волна 1–2): десятки–сотни событий/мин на заказ × число заказов/мин. При +100 заказов/мес + B2B-рост — **порядка нескольких GB в день** по всем сервисам (INFO), пиково больше при ошибках.
- Итого по горячему (30 дней, сжатие OpenSearch ~3–5x): **порядка 100–300 GB** на все системы в пиковом режиме. Хранится на 1–3 нодах OpenSearch (например, 3 × 100–200 GB NVMe) — реалистично в YC, управляемая стоимость.
- **Сэмплирование** (3.2): INFO по фоновым «здоровым» потокам можно сэмплировать (10–20%), а **ERROR/WARN/DLQ/сбойные заказы — 100%** (их никогда не теряем). Это режет объём без потери ценности (подход задания 3).

> **Итог:** отдельный индекс на систему, месячный rollover, 30/90 дней горячий + 12 мес cold, шифрование at rest, авто-удаление, сэмплирование INFO при сохранении 100% ошибок.

## 4. От сбора логов к их анализу: алертинг и поиск аномалий

Центральный журнал сам по себе — «пассивная» библиотека. Чтобы превратить его в **активную** систему анализа, добавляем два слоя: **алертинг по логам** и **поиск аномалий** (в т.ч. DDoS).

### 4.1. Нужен ли алертинг — да, и вот какой

Алертинг превращает «кто-то должен посмотреть логи» в «система сама позвонит, когда лог показывает беду». Используем **OpenSearch Alerting** (built-in, без дополнительных компонентов), роутинг — через общий **Alertmanager** (задание 2).

**Принцип:** алерт = **узор (pattern) в логах**, а не сырой лог. Каждый алерт — actionable: несёт `order_id`/`service`/ссылку на лог и трейс.

| # | Узор в логах (условие) | Источник | Уровень | Почему важно |
|---|---|---|---|---|
| **A1** | **ERROR** на любом этапе обработки заказа (с `order_id`) | MES/Shop/CRM API | **Critical** | Заказ сломан; нужен немедленный разбор. Нести `order_id` + трейс. |
| **A2** | **Сообщение в DLQ** (`event.type=DLQ` / `to_queue=dlq`) | RabbitMQ-интеграция | **Critical** | Заказ «потерялся» из рабочего потока. Каждое = потенциально потерянный заказ (S3). |
| **A3** | **ERROR/таймаут расчёта цены** (`event=PRICE_CALC`, `result=failure/timeout`) | MES API | **Critical** | Узкое место; заказ не может уйти в производство. |
| **A4** | **Рост доли ERROR (5xx) на API** за окно (тренд, не один лог) | Shop/CRM/MES API | **Critical** (B2B — сразу) | Деградация, видимая пользователям/партнёрам. Для B2B-сегмента MES API — алерт строже (SLA перед партнёром). |
| **A5** | **WARN: расчёт цены > 15 мин** (`event=PRICE_CALC` без `result` в окне) | MES API | Warning → Critical (30 мин) | Расчёт «ползёт» к потолку 30 мин — ранний сигнал зависания (S1). |
| **A6** | **WARN: повтор доставки** (`delivery_count > 1`) | RabbitMQ-интеграция | Warning | Повторы = маркер проблем с идемпотентностью/надёжностью (P4). |
| **A7** | **WARN: медленный запрос дашборда** (`event=LIST_ORDERS`, `duration > 2с`) | MES API | Warning | Прямое отражение жалобы операторов (S4). |
| **A8** | **ERROR: загрузка 3D-файла** (`event=FILE_UPLOAD`, `result=error`) | Shop API → S3 | Warning | Блокирует `FILE_UPLOADED`; массово = проблема S3/лимитов. |
| **A9** | **Рост ERROR в dev/release после деплоя** (сравнение с базовой линией) | все | Warning | Ранний лов регрессий **до** прода (важно при ручных деплоях). |

**Реакция (та же модель, что задание 2):** Warning → Telegram + тикет; Critical → Telegram + **звонок дежурному** + тикет highest; для B2B-critical — письмо партнёру (PM). В каждом алерте — `order_id`/`service` + **прямая ссылка на лог и трейс** (дежурный открывает в один клик).

**Анти-шум:** пороги калибруем после 2 недель (еженедельный разбор): цель — каждый critical-алерт = реальный инцидент, ≤ 5 critical/неделю.

### 4.2. Нужен ли поиск аномалий — да, и вот какой

Аномалии — это **не «ошибка в логе»**, а **«нечто, чего не должно быть по количеству/ритму»**. Пример из задачи: *было 4 записи о создании заказов в секунду, а стало 10 000* — это не ошибка, это **всплеск** (возможная DDoS-атака конкурентами или баг/ретрай-шторм). Для этого нужно два механизма:

**1. Пороговые/трендовые алерты (детерминированные аномалии) — через OpenSearch Alerting / дашборды:**

| Аномалия | Условие (узор в логах) | Тип угрозы | Реакция |
|---|---|---|---|
| **Всплеск создания заказов** | `count(event=ORDER_CREATED)` в 1 с/мин резко выше базовой линии (например, >10x от медианы за 7 дней, абсолютный порог на B2B-входе) | **DDoS / ретрай-шторм / баг** | **Critical:** звонок; проверка источника (один IP/партнёр?); **rate-limit** на MES API (задание 1, P7); блокировка аномального `partner_id`/IP; информирование PM. |
| **Всплеск 4xx/5xx от одного IP/партнёра** | `count(status=4xx/5xx) by client` аномально | Брутфорс/скан/сломанный интеграционный клиент | Блокировка IP/квота партнёра; тикет. |
| **Аномальный объём логов (log flood)** | `count(any log) per service` резко выше базовой (сервис «пишет по кругу» об ошибке) | Лог-шторм, скрывающий реальную проблему + DoS на хранилище | Ограничение/сэмплирование источника; тикет (сервис в «panicking»-состоянии). |
| **Аномальный рост DLQ** | `count(DLQ)` > порога в окно | Системная несовместимость (деплой) → массовые «отравленные» сообщения | Critical; разбор причины; возможный откат деплоя. |
| **Аномальный набор статусов** | `count(ORDER_STATUS_CHANGED to=X)` скачок в «невозможный» статус/ретрансляция | Баг в state-machine / дубликаты | Тикет; проверка идемпотентности. |

**2. Статистическое / ML-выявление аномалий** — через OpenSearch Anomaly Detection:

- Строим **детекторы** на ключевых счётчиках из логов: `ORDER_CREATED/сек`, `ERROR/мин по сервису`, `DLQ/мин`, `PRICE_CALC duration p95`.
- Детектор учит «нормальный» ритм (в т.ч. суточные/недельные паттерны: пики в рабочее время, тишина ночью) и **сам** сигналит на отклонение — без ручного подбора порогов.
- Результат детектора = **вход** в Alerting (Alert on anomaly score) → Alertmanager → дежурный.

> **Почему именно DDoS-пример решает аномалии, а не пороговый алерт:** порог «>N заказов/сек» нужно знать заранее и он слеп к «тихому» росту. Anomaly Detection ловит **отклонение от собственной базовой линии** сервиса — работает и на резкий скачок (10 000/с), и на «ползущий» рост, и на ночной аномальный трафик. Пороги + статистика = двойная страховка.

**3. Связка с другими слоями:** аномалия в логах **коррелируется** с метриками (задание 2: RPS, 5xx) и трейсом (задание 3: кто генерирует всплеск). В алерт-описании — «всплеск ORDER_CREATED с `partner_03`, 12:00, см. трейсы/метрики».

### 4.3. Итоговая модель «анализа логов»

```
Лог (JSON, trace_id/order_id)
  -> OpenSearch (индексы на систему, ILM)
  -> (a) Grafana Log Explorer   — ручной разбор по order_id/trace_id (MTTR)
  -> (b) OpenSearch Alerting    — алерты по узрам A1–A9 (A1–A9)
  -> (c) OpenSearch Anomaly Detection — аномалии ритма/объёма (DDoS, log flood)
  -> Alertmanager (общий) -> Telegram / тикет / звонок дежурного (+ письмо партнёру для B2B)
```

## 5. Дополнительное задание: критерии выбора технологии для работы с логами

Выбираем между четырьмя кандидатами: **ELK (Elasticsearch)**, **OpenSearch**, **Splunk**, **Loki** (Grafana). Критериев — 7 (больше пяти), взвешенных под контекст «Александрита» (9 человек + 1 DevOps, Yandex Cloud, рост нагрузки, уже есть OTel + Grafana + VictoriaMetrics, бюджет ограничен, Apache-лицензия предпочтительна).

| Критерий | ELK (Elasticsearch) | OpenSearch | Splunk | Loki (Grafana) |
|---|---|---|---|---|
| **1. Лицензия / стоимость владения** | Elastic License 2.0 (с 2021) / AGPL — **ограничения** на «коммерческое использование как сервис», часть фич (ML, некоторые alerting) — в платном Basic/Platinum | **Apache License 2.0** — свободно, без vendor-lock, фичи (Alerting, Anomaly Detection) — open-source | Проприетарная, **дорогая** (по объёму ingest/сжатых ГБ); enterprise-фичи платные | **Apache License 2.0** — бесплатно, дёшево в эксплуатации |
| **2. Полнотекстовый поиск / качество запросов** | Отличный DSL (Query DSL), высокая скорость, faceting | Отличный DSL (совместим с Elastic), faceting, aggs — **на уровне ES** | Сильный SPL, «лог-нативный» поиск | **Ограниченный** LogQL: хорошо label-фильтр, **слаб** полнотекст и aggs (не «поисковая система») |
| **3. Алертинг + аномалии (раздел 4)** | Alerting + ML-аномалии (часть — платная) | **Alerting + Anomaly Detection — built-in, open-source** | Топовый alerting + ML (дорогой) | Алертинг — только в Grafana (по логам), **ML-аномалии нет** (LogQL-правила) |
| **4. Интеграция с нашим стеком (OTel + Grafana + k8s)** | Поддерживается (OTel exporter), Grafana-datasource | **Поддерживается** (OTel exporter), Grafana-datasource; k8s-operator; **Yandex Cloud managed** | Свой агент (Splunk Universal Forwarder) — ещё один агент; Grafana-datasource есть | **Нативно в Grafana** (мы уже используем) + OTel exporter; самый лёгкий |
| **5. Операционная сложность / требования к ресурсам** | Тяжёлый (JVM, heap tuning), cluster overhead | Схож с ES (JVM), но **чуть легче** в эксплуатации; 1–3 ноды хватит | Платформа (forwarder+indexers+search heads) — **самая тяжёлая** в эксплуатации | **Самый лёгкий**: горизонтально-масштабируемые бинарники, минимум тюнинга |
| **6. Ретеншн / индексация / ILM (раздел 3.6)** | ILM, rollover, shrink/forcemerge — зрелые | **ILM, rollover, shrink, snapshots** — те же, что ES (совместимо) | Ретеншн по индексам/индексами — гибко, но дорого за объём | **Индексов нет** — «streams» (label-based); retention проще, но **нет «индекса на систему»** как класс (только labels) |
| **7. Зрелость / сообщество / vendor-risk** | Зрелый, большое сообщество, **риск** лицензионных изменений (уже меняли) | Зрелый (форк Amazon), крупное сообщество, **стабильная Apache-траектория** | Зрелый, «enterprise-grade», **высокий vendor-lock** | Зрелый в рамках Grafana, растёт, но **молодой** как «log-платформа» |

### 5.1. Плюсы / минусы (кратко)

- **ELK (Elasticsearch):** + самый зрелый поиск/ML, огромное сообщество. − **лицензия** (Elastic License, часть фич платная), **vendor-risk** (уже меняли лицензию), тяжёлый. *Вывод: отличная технология, но лицензионные/стоимостные ограничения при нашем бюджете и желании не зависеть от вендора.*
- **OpenSearch:** + **Apache 2.0** (свободно, не зависит от вендора), поиск/алерты/аномалии **на уровне ES и бесплатно**, OTel/Grafana/k8s-интеграции, управляемый вариант в YC, ILM/индексы на систему (раздел 3.6). − JVM-стек (требует тюнинга heap), «наследие ES». *Вывод: **лучший баланс** — все нужные фичи открыто + низкий vendor-risk.*
- **Splunk:** + «gold standard» лог-аналитики, сильнейший ML/алертинг. − **очень дорого** (по ingest), свой forwarder (лишний агент), **максимальный vendor-lock**, избыточно для 3 API + очередей. *Вывод: перебор по цене и сложности для нашего масштаба.*
- **Loki (Grafana):** + **нативно в Grafana** (уже есть), **самый лёгкий/дешёвый** в эксплуатации, Apache. − **слабый полнотекст/agg** (не поисковая система), **нет ML-аномалий**, «streams» вместо «индекса на систему». *Вывод: отличный **лёгкий MVP / фаза 1**, но не закрывает «анализ + аномалии + индекс на систему» из требований.*

### 5.2. Решение

**Основной выбор — OpenSearch.** Он закрывает **все** требования задачи (полнотекст, «индекс на систему» + ILM/retention, built-in **Alerting + Anomaly Detection**, OTel/Grafana/k8s-интеграции) на **Apache-лицензии** без vendor-lock и без enterprise-ценника Splunk. Инфраструктурные/лицензионные минусы ELK и Splunk, функциональные минусы Loki — не проходят по ключевым критериям (2, 3, 6).

**Практическая рекомендация по фазам:**
- **Фаза 1 (волны 1–2, MVP):** можно начать на **Loki** (дёшево, нативно в Grafana, быстро поднять) — закрыть «поиск по `order_id` + базовые алерты».
- **Фаза 2 (волны 3–4, анализ):** перейти/дополнить на **OpenSearch** — включить **Anomaly Detection** (DDoS/log-flood) и **индексы на систему** с ILM. Collector (OTel) позволяет менять бэкенд **без переделки приложений** (logs уходят в OTLP — смена target'а в конфиге Collector).

> Так мы получаем «быстрый старт» (Loki) и «целевое решение» (OpenSearch) на одном OTel-слое, не привязывая приложения к вендору хранилища.

## 6. Критерии успеха (как поймём, что логирование окупилось)

- Через 2 недели после волн 1–2: **ни одного «зависшего» заказа, о котором узнали только из жалобы клиента** — все потери замечены алертом (A1–A4).
- **MTTR** разбора «зависшего/потерянного» заказа: с «часов (ручной поиск по 5 системам, часть логов стёрта)» до **минут** (поиск по `order_id` + переход в трейс). М1.
- **MTTD**: с «недели/месяца (по жалобе)» до **минут** (алерт по ERROR/DLQ/5xx/аномалии). М2.
- **Coverage**: ≥ 95% заказов имеют полный централизованный лог по всем этапам (включая сбой). М3.
- **Ответ поддержки** на «где мой заказ»: с «часов/дня» до **минут** (готовый отчёт по `order_id`). М4.
- **B2B-партнёрам** — готовый факт-ответ «на каком этапе ваш заказ» по логам/трейсам (через обезличенный статус-эндпоинт), без ручного сбора.
- **Аномалии**: DDoS/всплеск `ORDER_CREATED` (кейс 10 000/с) обнаружен **автоматически** (Anomaly Detection) до потери SLA, а не по жалобам партнёров.
- **Снижение числа «сгоревших» заказов/контрактов в месяц** на фоне роста +100 заказов/мес. М5.
- **Гигиена**: в логах **нет** PII/секретов/содержимого 3D-моделей (проверено аудитом маскирования); каждый critical-алерт = реальный инцидент (≤ 5 critical/неделю).
